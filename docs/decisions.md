# Decisions

Choices made while building that the specification left open. Newest phase first.

## How changes are made

- **Spec signed off (2026-11-22):** [AI Workshop Platform: Spec](https://claude.ai/artifact/6mNkKPKQysWNoj7eL6Gyus), signed off by Franck, all 23 confirm-or-correct points confirmed.
- **Workflow:** each phase starts with a brief in `docs/phases/` and one round of questions.
  During a ticket, choices that can be undone are decided, recorded here and listed for veto in
  the pull request; only the cases under "Stop and ask" in `CLAUDE.md` wait for Franck. Each
  ticket is built in fresh-session tries and judged by the `checker` agent, at most 3 tries.
- **Spec deltas:** a change to signed-off behaviour is recorded here as ADDED, CHANGED or REMOVED,
  with the date and the pull request.

## Phase 0: foundations

- **AWS access:** least-privilege CloudFormation stack `ssd-workshop-access` (`infra/access/access-stack.yaml`): permissions boundary, GitHub OIDC deploy role limited to `main`, IAM user for Claude's sessions, $100/month budget. Rights are limited to `ssd-workshop-*` names, the `project=ssd-workshop` tag and DNS under `workshop.rankly.games`; the stack protects itself from the deploy role.
- **No CDK bootstrap roles:** CDK uses `CliCredentialsStackSynthesizer` with our own `ssd-workshop-cdk-assets-*` bucket, so deploys run with the least-privilege role instead of the account-wide `cdk-hnb659fds-*` roles. Stacks without file assets send their template inline instead (see "Synthesizers (0.4)").
- **Licence:** MIT, since the repository is public for the pitch.
- **Platform language:** TypeScript for infrastructure, API and web pages, so the platform is one language end to end; advanced participant apps use Python. (Franck, 2026-11-22)
- **SES:** already in production mode for rankly.games, so codes can go to any allow-listed address; sender `ssd-workshop@rankly.games`. (Franck, 2026-11-22)
- **Access stack split:** the deploy rights are two managed policies (`ssd-workshop-deploy` and `ssd-workshop-deploy-edge`), because IAM caps one managed policy at 6,144 characters.
- **Workspaces:** npm workspaces `infra` and `platform`; `templates/` holds only a README and becomes a workspace when it gets code.
- **Checks at the root:** one ESLint flat config (`@eslint/js` recommended + typescript-eslint strict), one strict `tsconfig.base.json` with a root `tsconfig.json` covering `infra/` and `platform/`, and vitest run from the root with `--passWithNoTests`. A workspace gets its own `tsconfig.json` when it gets code.
- **Tool versions:** ESLint 10, TypeScript 5.9 (typescript-eslint supports TypeScript below 6.1), vitest 5 (vitest 3 pulls a critical `tinypool` advisory).
- **Deny rules:** `.claude/settings.json` denies `cdk deploy/destroy/bootstrap`, `aws iam`, every CloudFormation stack write (not only `ssd-workshop-access`, since workshop stacks deploy from `main`), Route53 record changes, pushes to `main`, force pushes, and reading `.env*`, `secrets/`, keys and `~/.aws/credentials`.
- **Plugin for every session:** `.claude/settings.json` enables `spec-driven@cadenceworks` from the `cadenceworks-dev/claude-workflow` marketplace for local sessions; cloud sessions take it from the claude.ai account.
- **Path rules:** `.claude/rules/infra.md`, `platform.md` and `templates.md`.
- **Allowed without asking:** `.claude/settings.json` lets Claude sessions run `npm ci`, `npm run lint`, `npm run typecheck` and `npm test` without a permission prompt, since they touch only the working tree and the npm cache.
- **Engines:** `package.json` requires Node 22 or newer and npm 10 or newer, the versions CI and the cloud sessions use.
- **Limits of the deny rules:** `Read(...)` denies cover Claude's file tools; a shell `cat .env` or an `aws --profile x iam ...` form is not guaranteed to be caught. The real controls are that no secrets live in the repository and that the AWS user's least-privilege policy refuses what it must not do.
- **CI:** one GitHub Actions job `ci` on every pull request (npm ci, lint, type check, tests, `cdk synth`, `cfn-lint` on the access stack), so branch protection needs one required check. `permissions: contents: read` only, no AWS credentials, checkout without persisted credentials; cfn-lint pinned (`cfn-lint==1.61.0`) and installed with pip; actions pinned to major versions.
- **CDK runner:** `tsx` runs `infra/bin/app.ts` (`cdk.json` `app`), because it runs our ESM + `NodeNext` TypeScript with no extra config, where ts-node needs an ESM loader setup.
- **CDK and strict types:** aws-cdk-lib's declarations break `exactOptionalPropertyTypes`, so a synthesizer is asserted to `IStackSynthesizer` at the call site instead of turning the flag off. `@types/node` 22 is a root dev dependency for Node built-ins in tests.
- **CDK stacks (0.4):** three stacks: `ssd-workshop-cdk-assets` (eu-central-1, assets bucket), `ssd-workshop-site` (eu-central-1, private site bucket and its pages) and `ssd-workshop-edge` (us-east-1, certificate, CloudFront distribution and the `workshop.rankly.games` A/AAAA records). Deploy order assets, site, edge. Replaces the empty "first stack" of 0.3.
- **Distribution and record in the us-east-1 stack (0.4):** the brief put CloudFront and the DNS record in the site stack; they live with the certificate in `ssd-workshop-edge` because CloudFront and Route53 are global and the certificate must be in us-east-1. This avoids CDK cross-region references, which write SSM parameters under `/cdk/exports/` through a Lambda that the boundary and the deploy policy forbid. Nothing is passed between regions: the edge stack imports the site bucket by its fixed name and regional domain name.
- **Site bucket policy (0.4):** `s3:GetObject` only for the `cloudfront.amazonaws.com` service principal with `AWS:SourceAccount` = the account and `AWS:SourceArn` like `arn:aws:cloudfront::<account>:distribution/*`, plus the TLS-only deny. Any distribution of the account could read it, not only ours, because the distribution's id is in another region's stack; that includes the account's existing non-workshop distributions (rankly.games, www, play, letters and others), if one were pointed at this bucket with an Origin Access Control. Accepted because the bucket's content is public through CloudFront anyway. Narrowing `AWS:SourceArn` to our distribution needs its id, so it is a later second step (after the first deploy, the id goes into the site stack). Until then the site bucket must only ever hold public content: nothing private, no participant data.
- **Synthesizers (0.4):** only the site stack uses `CliCredentialsStackSynthesizer` with the assets bucket. That synthesizer uploads every stack's template to the assets bucket and deploys with `TemplateURL`, which cannot work for the stack that creates the bucket, nor for the us-east-1 stack (bucket in eu-central-1). The assets and edge stacks use `LegacyStackSynthesizer`: the CLI sends their template inline with the caller's credentials, no bootstrap roles, no `BootstrapVersion` parameter. They must have no file assets (a test guards it) and stay under 50 KB.
- **Fixed account (0.4):** the account id, region, hosted zone id and domain are constants in `infra/lib/config.ts`, so synth and tests run without AWS credentials and bucket names are literal (`ssd-workshop-site-<account>`). `config.ts` is the only place that holds the account id, zone id and boundary ARN, so the workshop can move to a dedicated AWS account by changing that one file: code and tests derive them from it (including the assets bucket name in the site stack's synthesizer, which no longer uses `${AWS::AccountId}`), and `infra/README.md` reads them from it instead of repeating them.
- **Boundary for every role (0.4):** `PermissionsBoundary.of(stack)` with the literal ARN `BOUNDARY_ARN` from `infra/lib/config.ts` (`arn:aws:iam::<account>:policy/ssd-workshop-boundary`), applied to each stack (an imported policy must live in a stack, so `PermissionsBoundary.of(app)` is not possible); a test checks every `AWS::IAM::Role`.
- **Pages upload (0.4):** `platform/web` is copied to the site bucket by `BucketDeployment` with `Cache-Control: public, max-age=60`, so a merged change is live within minutes without a CloudFront invalidation. Its Lambda function and role are named `ssd-workshop-site-deploy`, its AWS CLI layer `ssd-workshop-awscli` (CloudFormation would name the layer after its logical id, outside the deploy policy) and its logs go to the `ssd-workshop-site-deploy` log group with one week of retention. No `autoDeleteObjects` (extra Lambda); buckets are retained on stack deletion.
- **CloudFront settings (0.4):** Origin Access Control named `ssd-workshop-site` (CDK would generate a name outside `ssd-workshop-*`), redirect HTTP to HTTPS, `index.html` as default root object, managed `CachingOptimized` cache policy, `PriceClass_100` (North America and Europe), HTTP/2 and HTTP/3, TLS 1.2 (2021) minimum, IPv6 with an AAAA record. No custom cache or response headers policies and no CloudFront Functions.
- **Security headers (0.4):** the default behaviour uses the managed `SecurityHeadersPolicy` (`ResponseHeadersPolicy.SECURITY_HEADERS`): HSTS (one year, no `preload`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin` and `X-XSS-Protection`. Managed, so no new resource or cost; a Content-Security-Policy needs a custom policy and waits until the pages have scripts.
- **Names test (0.4):** the names test walks every resource's properties at any depth and requires every `*Name` key (such as `OriginAccessControlConfig.Name`) to start with `ssd-workshop-`, except DNS names (`DomainName`, `DNSName`, a record's `Name`), the bucket reference `DestinationBucketName` and `PolicyName` of inline role policies (not a resource of their own; their role is named).
- **Other sessions' worktrees (0.4):** `.claude/` is ignored by ESLint, excluded from vitest by a root `vitest.config.ts` (covered by the type check) and `.claude/worktrees/` is in `.gitignore`, so another session's checkout under `.claude/worktrees/` never changes lint, test or git results.
- **Placeholder page (0.4):** one self-contained `platform/web/index.html` ("SSD Workshop, coming soon" and one line on the workshop), system fonts, light and dark colours, no scripts or external requests.
- **Post-deploy checks (0.4):** the read-only commands for the criteria that need a live deploy are in `infra/README.md`; the zone snapshot for criterion 5 (`zone-before.json`) must be taken by Franck, or by a session with the read-only command, before ticket 0.5 is merged, and written outside the repository (`/tmp/`) so it is never committed, as is `zone-after.json`.
- **Deploy trigger (0.5):** `.github/workflows/deploy.yml` runs on `push` to `main` only: no `pull_request`, no `workflow_dispatch`, no tags. The role refuses other refs anyway; a redeploy of the same commit is a "Re-run all jobs" of the last run.
- **No GitHub environment (0.5):** the deploy job has no `environment:`, so its OIDC subject is `repo:kifbv/ssd-workshop:ref:refs/heads/main`, the only one the role trusts once the ticket 0.3 access stack update removes `environment:*`. Manual approval gates or environment secrets would need that line back; not needed while every merge is Franck's.
- **Deploy permissions and concurrency (0.5):** workflow-level `id-token: write` and `contents: read` only, checkout without persisted credentials, no `secrets.` references; `concurrency: deploy` with `cancel-in-progress: false`, so deploys run one at a time in merge order and a running CloudFormation update is never cancelled.
- **Role ARN from config.ts (0.5):** `DEPLOY_ROLE_NAME`/`DEPLOY_ROLE_ARN` live in `infra/lib/config.ts`; `infra/bin/print-deploy-settings.ts` (run with `tsx`) writes the role ARN, credentials region, site URL and the page's `<h1>` text to `$GITHUB_OUTPUT`, so the workflow holds no account id and the smoke check follows the page.
- **Deploy steps (0.5):** `npm ci`, `npm test` (cheap guard before touching AWS), settings, `aws-actions/configure-aws-credentials@v4` (session name `ssd-workshop-deploy-<run id>`), `npx cdk deploy --all --require-approval never` from `infra/`, smoke check. Lint, type check and synth are not repeated: CI ran them on the pull request and `cdk deploy` synthesizes.
- **Smoke check (0.5):** after the deploy, `curl` must get 200 from `https://workshop.rankly.games/` with the `<h1>` text of `platform/web/index.html`; 10 attempts 30 seconds apart (about five minutes, longer than the 60-second page cache), then the run fails. This is the proof of criterion 4 on every merge.
- **Deploy timeout (0.5):** 45 minutes for the job, since the first deploy creates a certificate (DNS validation) and a CloudFront distribution; later deploys take a few minutes.
- **`yaml` dev dependency (0.5):** `yaml` 2.x as a root dev dependency, so the tests parse `deploy.yml`, `ci.yml` and the access stack (with CloudFormation short-form tags) as data instead of matching text. Small, no dependencies, widely used; it was only in the lockfile as a nested copy inside `aws-cdk-lib` and as an optional peer of vite.
- **Trust test today (0.5):** the access stack test checks that the main subject is trusted and that no subject allows a pull request, another branch, a tag or the whole repository; it still accepts the `environment:*` line, because the 0.3 update is not on `main` yet. Once it is, the test should be tightened to "main only".
