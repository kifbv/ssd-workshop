# Decisions

Choices made while building that the specification left open. Newest phase first.

## How changes are made

- **Spec signed off (2026-11-22):** [AI Workshop Platform: Spec](https://claude.ai/artifact/6mNkKPKQysWNoj7eL6Gyus), signed off by Franck, all 23 confirm-or-correct points confirmed.
- **Workflow:** each phase starts with a brief in `docs/phases/` and one round of questions.
  During a ticket, choices that can be undone are decided, recorded here and listed for veto in
  the pull request; only the cases under "Stop and ask" in `CLAUDE.md` wait for Franck. Each
  ticket is built in fresh-session tries and judged by the `checker` agent, at most 3 tries.
- **Spec deltas:** a change to signed-off behaviour is recorded here as ADDED, CHANGED or REMOVED,
  with the date and the pull request.

## Phase 0: foundations

- **AWS access:** least-privilege CloudFormation stack `ssd-workshop-access` (`infra/access/access-stack.yaml`): permissions boundary, GitHub OIDC deploy role limited to `main`, IAM user for Claude's sessions, $100/month budget. Rights are limited to `ssd-workshop-*` names, the `project=ssd-workshop` tag and DNS under `workshop.rankly.games`; the stack protects itself from the deploy role.
- **No CDK bootstrap roles:** CDK uses `CliCredentialsStackSynthesizer` with our own `ssd-workshop-cdk-assets-*` bucket, so deploys run with the least-privilege role instead of the account-wide `cdk-hnb659fds-*` roles.
- **Licence:** MIT, since the repository is public for the pitch.
- **Platform language:** TypeScript for infrastructure, API and web pages, so the platform is one language end to end; advanced participant apps use Python. (Franck, 2026-11-22)
- **SES:** already in production mode for rankly.games, so codes can go to any allow-listed address; sender `ssd-workshop@rankly.games`. (Franck, 2026-11-22)
- **Access stack split:** the deploy rights are managed policies of at most 6,144 characters each (IAM's cap): `ssd-workshop-deploy` and `ssd-workshop-deploy-edge`, plus `ssd-workshop-deploy-read` since try 3 of ticket 0.3.
- **Workspaces:** npm workspaces `infra` and `platform`; `templates/` holds only a README and becomes a workspace when it gets code.
- **Checks at the root:** one ESLint flat config (`@eslint/js` recommended + typescript-eslint strict), one strict `tsconfig.base.json` with a root `tsconfig.json` covering `infra/` and `platform/`, and vitest run from the root with `--passWithNoTests`. A workspace gets its own `tsconfig.json` when it gets code.
- **Tool versions:** ESLint 10, TypeScript 5.9 (typescript-eslint supports TypeScript below 6.1), vitest 5 (vitest 3 pulls a critical `tinypool` advisory).
- **Deny rules:** `.claude/settings.json` denies `cdk deploy/destroy/bootstrap`, `aws iam`, every CloudFormation stack write (not only `ssd-workshop-access`, since workshop stacks deploy from `main`), Route53 record changes, pushes to `main`, force pushes, and reading `.env*`, `secrets/`, keys and `~/.aws/credentials`.
- **Plugin for every session:** `.claude/settings.json` enables `spec-driven@cadenceworks` from the `cadenceworks-dev/claude-workflow` marketplace for local sessions; cloud sessions take it from the claude.ai account.
- **Path rules:** `.claude/rules/infra.md`, `platform.md` and `templates.md`.
- **Allowed without asking:** `.claude/settings.json` lets Claude sessions run `npm ci`, `npm run lint`, `npm run typecheck` and `npm test` without a permission prompt, since they touch only the working tree and the npm cache.
- **Engines:** `package.json` requires Node 22.21 or newer (built-in `proxyEnv`, used by the smoke script behind a proxy) and npm 10 or newer, the versions CI and the cloud sessions use.
- **Limits of the deny rules:** `Read(...)` denies cover Claude's file tools; a shell `cat .env` or an `aws --profile x iam ...` form is not guaranteed to be caught. The real controls are that no secrets live in the repository and that the AWS user's least-privilege policy refuses what it must not do.
- **CI:** one GitHub Actions job `ci` on every pull request (npm ci, lint, type check, tests, `cdk synth`, `cfn-lint` on the access stack), so branch protection needs one required check. `permissions: contents: read` only, no AWS credentials, checkout without persisted credentials; cfn-lint pinned (`cfn-lint==1.61.0`) and installed with pip; actions pinned to major versions.
- **CDK runner:** `tsx` runs `infra/bin/app.ts` (`cdk.json` `app`), because it runs our ESM + `NodeNext` TypeScript with no extra config, where ts-node needs an ESM loader setup.
- **First stack:** the CDK CLI refuses to synthesize an app with no stacks, so the app holds one empty `ssd-workshop-site` stack (eu-central-1, `CliCredentialsStackSynthesizer` with the `ssd-workshop-cdk-assets-<account>` bucket, `project=ssd-workshop` tag on the whole app) that ticket 0.4 fills.
- **Access stack test:** `infra/access/access-stack.test.ts` parses the template with the `yaml` package (dev dependency of `infra`; built-in types and custom tags for `!Ref`/`!Sub`/`!GetAtt`/`!Equals`, where `js-yaml` needs `@types/js-yaml` and a schema) and checks both deploy policies statically, with every unscopable write on a commented allow-list keyed by statement and action.
- **Access stack tightened (ticket 0.3):** `CreateServiceLinkedRole` moved to its own statement so the other role housekeeping rights no longer reach `aws-service-role/*`; CloudFront function rights limited to `function/ssd-workshop-*`; `ProtectThisStack` denies every non-read CloudFormation action on `ssd-workshop-access` (adds cancel, rollback and stack policy to update, delete and change sets).
- **Access stack, try 2 of ticket 0.3 (the stack is live, so Franck applies this with "Update stack"):**
  - *Tags:* `cloudfront:TagResource` and `acm:AddTagsToCertificate` moved from the create statements (request tag only, so the role could tag any distribution or certificate and then change it) to the change statements, which need `aws:ResourceTag/project=ssd-workshop`. AWS authorizes the tag action again when a resource is created with tags (CreateDistributionWithTags, RequestCertificate with tags); ACM documents that the resource tag then holds the tags being applied, CloudFront is proven by ticket 0.4. Other tag rights: `ec2:CreateTags` only through `ec2:CreateAction` or the resource tag, `lambda:TagResource` on functions by name and on event source mappings, `iam:TagRole` on `ssd-workshop-*` roles (never the deploy role).
  - *API Gateway:* the region-wide `ApiGatewayInRegion` is replaced by `POST /restapis` and `POST /apis` with the request tag, and writes under `/restapis/*` and `/apis/*` with the resource tag (child resources inherit the API's tag for authorization). Not granted: `/tags/*` (changing an API's tags after creation), `/account` (account-wide CloudWatch role), domain names, API keys, usage plans.
  - *Own identities:* `ProtectAccessIdentities` denies every IAM action except `Get*`/`List*` on the role `ssd-workshop-deploy`, the user `ssd-workshop-claude` and the policies `ssd-workshop-boundary`, `ssd-workshop-deploy` and `ssd-workshop-deploy-edge`, because `role/ssd-workshop-*` also matches the deploy role.
  - *PassRole:* own statement, `iam:PassedToService` limited to `lambda`, `ecs-tasks`, `ec2`, `states`, `scheduler` and `events` (`.amazonaws.com`). Not `cloudformation`: the CLI-credentials synthesizer passes no stack role.
  - *Service-linked roles:* `iam:AWSServiceName` `ecs.amazonaws.com` only (ECS builds); spot or Auto Scaling roles are added if the k3s cluster needs them.
  - *Other writes:* event source mappings need `lambda:FunctionArn` `ssd-workshop-*`; `lambda:TagResource` (unnamed) only on event source mapping ARNs; `scheduler:CreateScheduleGroup` only on `schedule-group/ssd-workshop-*`; `ecs:CreateCluster` and `ecs:RegisterTaskDefinition` only by name (`cluster/ssd-workshop*`, `task-definition/ssd-workshop*`, both have a resource type), stricter than a request-tag condition; `ec2:RunInstances` needs the project tag on the subnet, security groups and launch template, and allows any AMI and new network interfaces in this account; key pairs are no longer allowed (k3s nodes use Systems Manager). Still unscoped because AWS offers only `Resource *`: `ecs:DeregisterTaskDefinition`, `logs:CreateLogDelivery`, `logs:DeleteLogDelivery`.
  - *Names:* log groups are `ssd-workshop-*`, `/aws/lambda/ssd-workshop-*` and `/ecs/ssd-workshop-*` (deploy policy and boundary) instead of `*ssd-workshop*`; `WorkshopStacks` lost the `changeSet/*` resource, since change set actions authorize against the stack ARN.
  - *Test:* a name counts as scope only when it starts with `ssd-workshop` after the resource type; a tag-adding action with only a request tag always fails; `ec2:CreateAction` counts only for creates that need the project tag; each hole class has a test that runs the old pattern and expects a failure; the policy sizes are checked against 6,144 characters.
- **Access stack, try 3 of ticket 0.3: shared account (Franck, 2026-11-22: the workshop stays in the rankly.games account, which also runs the rankly.games, www, play and letters distributions; Franck applies this with "Update stack").** Every hole IAM can close is closed; what remains is in `infra/access/README.md`, "Accepted risks".
  - *Reads:* a third managed policy `ssd-workshop-deploy-read` (attached to the deploy role and the Claude user, protected by `ProtectAccessIdentities`) holds the reads, because `ssd-workshop-deploy` would pass 6,144 characters. Account-wide only reads without secrets (stack list, template validation, `ec2:Describe*`, `ecs:List*`, certificates, hosted zone list, Bedrock models and inference profiles, service quotas, SES account and identities, bucket and log group names, costs). Removed account-wide: `lambda:List*`, `ecs:Describe*`, `apigateway:GET`, `cloudformation:Describe*`/`ListExports`/`GetTemplateSummary`, `iam:Get*`/`List*`, `cloudfront:Get*`/`List*`, `ses:Get*`/`List*`, `bedrock:Get*`/`List*` (models and inference profiles only), `logs:Describe*` (log groups only), `ssm:DescribeParameters`, `budgets:View*` (the workshop budget only), `sts:GetCallerIdentity` (needs no permission). Reads on workshop scope instead: stacks `ssd-workshop-*` (CDK names the stack), functions, ECS and other named resources by name, IAM on `/ssd-workshop/` roles and instance profiles and `ssd-workshop-*` policies, APIs and distributions by project tag, the rankly.games zone. Explicit denies: `ec2:DescribeInstanceAttribute`, `DescribeLaunchTemplateVersions`, `DescribeSpotFleetRequests` and `DescribeSpotInstanceRequests` outside the project tag (user data; the last three have no resource tag, so they are denied everywhere) and `apigateway:GET` on `/apikeys*`.
  - *ECS task definitions:* `ecs:DescribeTaskDefinition` supports only `Resource *` and returns every task definition's environment, so it is not granted; the first ticket that deploys one brings the choice to Franck (grant on `*`, or a CloudFormation service role).
  - *CloudFront parts without tags:* create and read only (`CreateOriginAccessControl`, `CreateCachePolicy`, `CreateOriginRequestPolicy`, `CreateResponseHeadersPolicy`); no update or delete on `*`, so the other distributions' policies and origin access controls are safe. Ticket 0.4 uses AWS-managed cache and response-headers policies and `RemovalPolicy.RETAIN` on its origin access control.
  - *EC2 instances:* `RunInstances` on images only with `ec2:Owner` `amazon` (k3s nodes use Amazon Linux 2023); instance, volumes and new network interfaces with the project request tag; subnets, security groups, launch templates and existing network interfaces with the project resource tag. `RunInstances` is no longer in the request-tag statement on `*`.
  - *IAM path:* workload roles and instance profiles live under `/ssd-workshop/`; every role right (create, policies, housekeeping, `PassRole`, boundary `PassRole`) is on `role/ssd-workshop/*` and `instance-profile/ssd-workshop/*`, which structurally excludes the deploy role (path `/`). `iam:UpdateAssumeRolePolicy` stays: CloudFormation changes a role's trust in place when CDK's `assumedBy` changes, and dropping it would not close outside trust anyway, since `CreateRole` sets any trust policy.
  - *No self-assume:* explicit deny of `sts:AssumeRole`, `sts:TagSession` and `sts:SetSourceIdentity` for both principals, because a role whose trust policy names a principal of the same account needs no identity allow.
  - *Boundary:* `ecs:RunTask` only on `task-definition/ssd-workshop-*` with `ecs:cluster` `cluster/ssd-workshop-*`; stop and describe on `task/ssd-workshop-*/*`; image pulls on `repository/ssd-workshop-*`; invalidations on tagged distributions; `cloudwatch:PutMetricData` only in the namespace `ssd-workshop`; `ssm:UpdateInstanceInformation` only on instances tagged with the project; `PassRole` only `/ssd-workshop/` roles to `ecs-tasks.amazonaws.com`. The boundary goes through the same scope test as the deploy policies, with its own exception list.
  - *Budget:* `budgets:ModifyBudget` removed; only `ViewBudget` on `ssd-workshop-monthly`.
  - *S3:* every bucket grant (deploy and boundary) also needs `aws:ResourceAccount` = this account, because bucket names are global.
  - *Names:* `ssd-workshop-*` with the dash everywhere (ECR repositories, ECS clusters, services, tasks and task definitions were `ssd-workshop*`); the test rejects names without the dash.
  - *DNS:* record types limited to `A`, `AAAA`, `CNAME`, and a `Null` guard on the record-name and record-type keys (`ForAllValues` is true when the key is missing).
  - *Sharing outside the account:* denied for both principals: S3 bucket and object ACLs, Secrets Manager, ECR, DynamoDB, SSM and CloudWatch Logs resource policies, Lambda function URLs and layer permissions, SQS and SNS `AddPermission`, DynamoDB exports, log subscription filters; `lambda:AddPermission` only for API Gateway, EventBridge, SNS and S3; EventBridge targets only in this account; SNS subscriptions only to workshop Lambda functions and queues. Kept, and listed as accepted risks: `s3:PutBucketPolicy` (CDK writes the bucket policy for the CloudFront origin access control), SQS and SNS policies set as attributes.
  - *Size:* `Bedrock` and `SesForTesting` moved from `ssd-workshop-deploy` to `ssd-workshop-deploy-edge` to keep each policy under 6,144 characters.
  - *Recommended to Franck:* enable the free IAM Access Analyzer external-access analyzer for the account, to see any role or resource policy shared outside it.
- **Access stack, try 4 of ticket 0.3 (last try, approved by Franck; the workshop stays in the shared rankly.games account; Franck applies this with "Update stack").** Every hole IAM can close is closed; the rest is listed in `infra/access/README.md`, "Accepted risks" (now 14 items).
  - *EC2 parents:* a request tag is true for every resource a call names, also existing parents. The EC2 rights move to a fifth managed policy `ssd-workshop-deploy-ec2` (attached to both principals, protected by `ProtectAccessIdentities`). Request-tag statements list only ARN types that are new in every call of their actions (`Ec2NewTopLevel`, `Ec2NewInVpc`, `Ec2NewAttached`); the parents (VPC, subnet, security group, route table, Elastic IP, network interface, launch template) need the project resource tag (`Ec2ParentsTagged`). Resource types per action were read from the AWS Service Authorization Reference (machine-readable `servicereference.us-east-1.amazonaws.com/v1/ec2/ec2.json`, 2026-11-22). `CreateVolume` from any snapshot is denied. `ec2:CreateNetworkInterface` is added (request tag on the interface, resource tag on subnet and security groups).
  - *RunInstances network interfaces:* only with the project resource tag. A network interface that `RunInstances` creates has no resource tag, so the k3s ticket creates the node's interface first and passes its id in the launch template (rules in `.claude/rules/infra.md`). This rules out Auto Scaling groups for k3s nodes until revisited.
  - *ECS:* deny `ecs:RunTask` and `ecs:StartTask` unless `ecs:cluster` is `cluster/ssd-workshop-*`. `CreateService`/`UpdateService` authorize on the service ARN, which holds the cluster name (`service/ssd-workshop-*/*`), so no extra deny is needed; `CreateTaskSet` is not granted.
  - *EventBridge:* deny `events:PutRule` when `events:source` names anything other than `ssd-workshop.*`, and when the pattern has no source (a pattern without one, or a schedule rule, matches every project's events).   - *ACM:* `RequestCertificate` needs `acm:DomainNames` within `workshop.rankly.games` and `*.workshop.rankly.games`, with a `Null` guard.
  - *SES:* sends only on `identity/ssd-workshop@rankly.games` and `identity/rankly.games` (any region of this account; SES authorizes the domain identity when the address is not verified on its own), still pinned by `ses:FromAddress`. No configuration set is granted.
  - *Reads:* `ec2:DescribeVpnConnections` denied everywhere (VPN pre-shared keys); `ses:GetAccount` removed (contact addresses).
  - *Sharing and egress:* added to `NoExternalSharing`: `logs:CreateExportTask`, `s3:PutBucketLogging`, `s3:PutInventoryConfiguration`, `s3:PutAnalyticsConfiguration`, `s3:PutReplicationConfiguration` and, for the deploy principals, `s3:PutBucketNotification` (none has a condition key for the destination).   - *Policy layout:* the sharing denies moved from `ssd-workshop-deploy` to `ssd-workshop-deploy-edge` (which lost the EC2 statements) to keep every policy under 6,144 characters. Sizes: boundary 3,634, deploy 5,170, edge 4,527, ec2 3,114, read 2,264.
  - *Test:* a request tag on `Resource "*"` counts as scope only for actions on a commented list (`cloudfront:CreateDistribution`, `acm:RequestCertificate`, which authorize no existing resource); an `EC2_PARENTS` table fails any request-tag statement that lists a parent ARN of its actions; new checks for ECS clusters, EventBridge sources, ACM names, SES identities, the boundary's sharing denies, VPN and SES account reads, and GitHub workflows (only `deploy.yml`, on push to `main`, may request `id-token: write` or `write-all`).

- **Access stack, tag on create (ticket 0.3, after try 4; found by the ticket 0.4 thread).** CloudFormation creates a distribution with `CreateDistributionWithTags` and a certificate with tags; AWS then also checks `cloudfront:TagResource` / `acm:AddTagsToCertificate`, which were allowed only on resources already tagged, so the first edge deploy would fail. `TagOnCreateThroughCloudFormation` allows both with the project request tag, no project tag on the resource yet, and `aws:CalledVia` CloudFormation; `NoResourceImport` denies change sets that import existing resources, the only CloudFormation path to an existing resource. Needs live proof in ticket 0.4 that CloudFormation sets `aws:CalledVia` for these calls; if it does not, the deploy fails safely (no wider right is granted). Sizes: deploy 5,338, edge 4,854.
- **Deploy role trust: `main` only.** The role trusts only the subject `repo:kifbv/ssd-workshop:ref:refs/heads/main`; the `environment:*` entry is gone. Ticket 0.5's deploy job therefore uses no GitHub environment (an environment changes the OIDC subject to `environment:<name>`, which the role refuses).
- **After applying the access stack:** Franck deactivates the admin access keys used so far once the `ssd-workshop-claude` key works (README step 7).
- **CDK and strict types:** aws-cdk-lib's declarations break `exactOptionalPropertyTypes`, so a synthesizer is asserted to `IStackSynthesizer` at the call site instead of turning the flag off. `@types/node` 22 is a root dev dependency for Node built-ins in tests.
- **Smoke checks (0.6):** `npm run -s smoke -- bedrock | quota | ses <address>` at the root runs `platform/src/smoke/main.ts` with `tsx`; the rules (arguments, quota matching, masking, latency) are pure functions in `logic.ts` with vitest tests, the AWS calls stay thin. Unknown command or missing address prints usage and exits 1, before any AWS call.
- **Smoke run silently:** npm echoes every script's command line (`> tsx src/smoke/main.ts ses jane@...`), which would print the recipient address. The root script calls the workspace with `npm run -s`, which silences the inner echo; the outer echo can only be silenced by the caller, so the command is documented (usage text, `main.ts` header, here) as `npm run -s smoke -- ses <address>`.
- **Smoke model:** defaults to `eu.anthropic.claude-sonnet-5-5` (latest Sonnet, EU inference profile, as the spec says Sonnet), overridable with `SMOKE_MODEL_ID`. Its applied cross-region tokens-per-minute quota in eu-central-1 is 0 (AWS default 6,000,000), so until a quota increase is granted `bedrock` needs `SMOKE_MODEL_ID=eu.anthropic.claude-sonnet-4-6`; an id that does not start with `eu.anthropic.` is refused. Converse API, one-word prompt, `maxTokens` 16.
- **Smoke quotas:** matched by name on Service Quotas code `bedrock`: `Cross-region model inference tokens|requests per minute for Anthropic Claude <Family> <x.y>`, optional ` V1`; the `Global cross-region` and `1M Context Length` variants are left out, since `eu.*` profiles are geographic cross-region. Prints the applied value next to the AWS default. Sonnet 5.5 has no requests-per-minute quota in the list, so the script says so.
- **Smoke email:** SESv2 `SendEmail` from `ssd-workshop@rankly.games`, subject "SSD Workshop smoke test", a random sample 6-digit code. The recipient is printed masked (`f***@e***.com`); error messages are printed with credentials in URLs replaced (`scheme://***@`) and addresses masked; the MessageId is printed. Limit: the script masks only its own output; npm's command echo shows the full address unless the command is run with `npm run -s` (see "Smoke run silently").
- **Smoke proof without a real inbox:** the SES mailbox simulator (`success@simulator.amazonses.com`) only proves that SES accepted the send from `ssd-workshop@rankly.games`. The two `ses` acceptance criteria (arrival at a verified and at an unverified real address) need Franck to run the command and check the inboxes.
- **Smoke dependencies:** `@aws-sdk/client-bedrock-runtime`, `@aws-sdk/client-service-quotas`, `@aws-sdk/client-sesv2` (official AWS SDK v3 clients) as platform dependencies; `tsx` as a platform dev dependency, as in `infra`.
- **AWS SDK behind a proxy:** the SDK ignores `HTTPS_PROXY`; when it (or lowercase `https_proxy`) is set, the clients get an `https.Agent` with Node's built-in `proxyEnv` (Node 22.21+), so no proxy-agent dependency is needed.
