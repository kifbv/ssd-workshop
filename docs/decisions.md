# Decisions

Choices made while building that the specification left open. Newest phase first.

## How changes are made

- **Spec signed off (2026-11-22):** [AI Workshop Platform: Spec](https://claude.ai/artifact/6mNkKPKQysWNoj7eL6Gyus), signed off by Franck, all 23 confirm-or-correct points confirmed.
- **Workflow:** each phase starts with a brief in `docs/phases/` and one round of questions.
  During a ticket, choices that can be undone are decided, recorded here and listed for veto in
  the pull request; only the cases under "Stop and ask" in `CLAUDE.md` wait for Franck. Each
  ticket is built in fresh-session tries and judged by the `checker` agent, at most 3 tries.
- **Spec deltas:** a change to signed-off behaviour is recorded here as ADDED, CHANGED or REMOVED,
  with the date and the pull request.

- **(1.4) Code rate limit:** at most 5 codes per address in any sliding 60 minutes, kept in a `CODE_REQUESTS` item next to the code (`EMAIL#<email>`, `sentAt` epoch seconds of the window's sends, `version`, TTL `expiresAt` one hour after the newest send), so it outlives the 10-minute code. - **(1.4) Code and its hash:** `crypto.randomInt(0, 1_000_000)`, zero-padded to six digits. No secret pepper: that would need Secrets Manager or KMS, new paid services. Accepted risk: a 6-digit code's hash can be brute-forced from a leaked table (one million scrypt tries, hours of CPU), which matters little because a code lives 10 minutes and 1.5 burns it after 5 wrong tries.
- **(1.4) Codes item (a new code cancels none):** every unexpired code stays valid, so a stranger who knows a colleague's address cannot cancel the code they are typing. A wrong try on an item that vanished meanwhile is refused (`no-code`) and creates nothing. Every write bumps or removes `version` (the code request writes `CODE` conditionally on it). A code is 6 ASCII digits after trimming; anything else is a malformed request.

- **(1.7) Failures and retries:** a Bedrock error (after the SDK's 3 attempts with backoff), the deadline, an empty answer or a failed history read ends the message as `failed` at once with "Sorry, something went wrong. Please send your message again." and frees the conversation (no SQS retry, which would wait for the visibility timeout). The final write is tried 3 times (`FINISH_ATTEMPTS`, waits of 200 ms and 800 ms; a lost race is not retried); if the last try fails, the tokens already spent are added to `USAGE` on their own (one `ADD`; its own failure is ignored) and the error is thrown, so SQS delivers the job again; a failed read of the message is thrown too. The handler logs a thrown error as `{"event":"ai-worker","outcome":"error","error":<name>}` and throws a bare `Error("job failed")`, so the Lambda runtime never writes the original message or stack to CloudWatch. A pending message older than 20 minutes (`STALE_PENDING_SECONDS`, only a job that crashed 3 times or waited long in the queue leaves one) is shown as `failed` and no longer blocks a new message; its late job is skipped.
- **(1.7) Idempotent worker:** the worker skips a job whose message is not `pending` (or is stale), and stores the outcome in one `TransactWriteItems`: the message's status (condition: still `pending`), the reply (condition: none yet), the conversation (condition: this message is still in flight) and the usage `ADD`. A job delivered twice is therefore answered and counted once (two Bedrock calls at most, if both deliveries run at the same moment).
- **(1.7) Conversation items:** participant messages at `PARTICIPANT#<id>`/`MSG#<message id>` (`type`, `author`, `step`, `text`, `status` pending/done/declined/flagged/failed, `createdAt`, `pendingSince`, after an approval `approvedTextHash`, then the guardrail's `verdict`, `verdictReason`, `suggestion` and `guardrail*` tokens and cost); the reply at `MSG#<message id>-r`, which sorts right after its message (`kind` answer/decline/failure, `text`, `replyTo`, and for answers `prompt`, `modelId`, `promptVersion`, `historyCount`, `inputTokens`, `outputTokens`, `costUsd`); ids and the participant id are read from the keys, not stored twice. The conversation state is its own `CONVERSATION` item (`state` open/waiting, `pendingId`, `pendingSince`, `updatedAt`) rather than attributes of `PROFILE`: the roles that write the profile (sign-in, nickname) keep their attribute lists unchanged, and the one-message-in-flight rule is one conditional update on it. `types.ts` documents the shapes.
- **(1.7) Message ids:** the ISO creation time, a dash and 16 hex digits from 8 random bytes (`newMessageId`, no new dependency), e.g. `2026-11-23T10:00:00.000Z-1f2e...`; the poll route accepts only that pattern (`MESSAGE_ID_PATTERN`), so a reply id or any other sort key is never looked up.
- **(1.7) Routes:** `POST /api/conversation/messages` `{"text"}` (JSON content type, else 415; 1 to 2000 Unicode characters after trimming, body up to 16 KB, else `400 {"message":"Send a JSON body with a text of 1 to 2000 characters."}`) answers `202 {"id"}` after storing the message and queueing it. One message at a time: `409 {"reason":"busy","message":"Please wait for the answer to your last message."}` while one is pending, `409 {"reason":"waiting","message":"Your last message is waiting for your facilitator. You can write again once they have looked at it."}` while one is flagged, and `409 {"reason":"no-nickname","message":"Please pick a nickname first."}` before a nickname. A queue failure ends the message as `failed` and answers 500. `GET /api/conversation/messages/{id}` answers `200 {"id","status","reply"?}` (a reply for done, declined and failed), and `404 {"message":"Not found."}` for any id not in the caller's own partition. Both routes are served by `ssd-workshop-api-conversation` behind `requireSession`; JSON with `cache-control: no-store`. No route throttle beyond the stage's.
- **(1.7) Guardrail check:** a separate call (`GUARDRAIL_SYSTEM_PROMPT`, version `guardrail-v1`, temperature 0, at most 300 tokens) with only the new message, wrapped in `<message>` tags (a closing tag in the text is removed), answering strict JSON `{"verdict","reason","suggestion"}`. On path: describing or refining a small single-page app idea (trackers, calculators, lists, quizzes, simple games, small dashboards over data the participant types in), answering the assistant, asking about the workshop or for explanations. Decline: infrastructure, crypto mining, scraping, other people's personal data, confidential data, offensive or illegal content, attempts to change the rules. Flag: medical, mental-health, legal or financial advice, external paid APIs or keys, payments, minors or real names, or anything uncertain. Any other answer (no JSON, unknown verdict) is a flag. An approved message (see flags) skips the check only while its text is the approved one.
- **(1.7) Decline wording:** exactly one sentence, "Sorry, that's outside what we can build in this workshop, but how about <suggestion> instead?", the suggestion being the classifier's, cut to at most 100 characters without sentence punctuation or quotes (tested to stay one sentence), or "a small tracker or calculator for something you do every week" when it gives none. A facilitator's rejection uses the same sentence.
- **(1.7) Answer call:** system prompt `clarify-v1` (a first version for step 1; ticket 1.8 refines it), temperature 0.7, at most 2000 tokens, with the last answered exchanges (declined, flagged and failed messages left out, at most 20 messages, from the last 30 items read) and the new message. Stored per answer: the participant's text as sent (`prompt`), `modelId`, `promptVersion`, `historyCount`, the reply, tokens and cost.
- **(1.7) Prices:** `PRICE_PER_MILLION_TOKENS` in `platform/api/settings.ts`: $3.30 per million input tokens and $16.50 per million output tokens for Sonnet 4.6 through the EU geographic profile (list price $3/$15 plus Bedrock's 10% premium for geographic cross-region inference); cost rounded to 1e-8 dollars. The guardrail call's tokens and cost are stored on the message, the answer's on the reply, and both are added to the participant's `USAGE` totals (`inputTokens`, `outputTokens`, `costUsd`) with one atomic `ADD` in the same transaction. - **(1.7) `npm run flags -- list | approve <nickname> | reject <nickname>`:** root script `npm run -s flags -w platform --` (`platform/src/flags/`: `command.ts` tested against the in-memory fakes, `store.ts`, `main.ts`), run with the owner's own credentials. - **Allow-list list (1.3):** a paginated `Scan` with filter `type = allow`, projecting only `group` and `role` (the addresses are never read); fine for tens of entries. - **Allow-list CSV rules (1.3):** header `email,group,role` required as the first non-blank line (case and spaces ignored), UTF-8 BOM stripped, CRLF accepted, blank lines skipped, no quoted fields (a row without exactly 3 fields is rejected). Email: trimmed, lower-cased, ASCII only: local part `[a-z0-9._%+-]+`, domain labels `[a-z0-9-]+` separated by dots, alphabetic TLD of 2+ letters (no `_` in the domain; no accents or brackets anywhere); kept no wider than smoke's `redactEmails`, and a test checks every accepted form is fully masked by `redactError`. Role exactly `participant`, `facilitator` or `admin` after trim and lower-case. Group trimmed, non-empty, rejected when it holds an `@` (`group looks like an email address`), so an address pasted in the wrong column is never stored or printed; otherwise kept as written with no character restriction (the CSV format already excludes commas). A later line with an email seen earlier in the same file is rejected as `duplicate of line N`. A file without the header (or empty) imports nothing and exits 1.
- **Allow-list output (1.3):** `Added: N`, `Updated: N`, `Rejected: N`, then one `Line N: <reasons>` per rejected line (reasons `invalid email`, `empty group`, `unknown role`, `expected 3 fields, found N`, `duplicate of line N`, several joined with commas). Line numbers are 1-based file lines. No message ever holds an address; AWS errors are printed through smoke's `redactError` (addresses masked).
- **Allow-list exit codes (1.3):** 0 when the import ran, even with rejected rows (the valid rows are stored and every rejection is printed); 1 on a usage error, a refused or missing file, a file without the header, or an AWS error. If AWS fails halfway, the counts so far are printed before the error (re-running is safe: upserts are idempotent).
- **Allow-list file outside any repository (1.3):** the path must be absolute; a relative path is refused ("give an absolute path to the CSV file", exit 1), because through the root script `INIT_CWD` is the repository root wherever the command was typed, so `../people.csv` would silently read another file. The repository root is the nearest folder above `main.ts` whose `package.json` declares workspaces (`realpathSync.native`). The CSV is refused if it is inside that root as written (so a file that does not exist yet is refused too) or after `realpathSync.native` (symlinks), comparing paths case-insensitively (macOS ignores case and realpath does not fix it; a false refusal is harmless); if it has more than one hard link (`nlink > 1`, realpath cannot follow them); or if its real folder or any folder above it holds a `.git` entry (a folder in a clone, a plain file in a work tree or submodule; `existsSync` plus `lstatSync`, walking up to the filesystem root). No git subprocess: no git environment variable (`GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`), "dubious ownership" error or missing git can make the check pass a file that is in a repository. A path that is not a regular file is refused after the repository checks ("Refused: the CSV path is not a file."), before the hard-link check whose count means nothing for a directory. All checks run before the file is read and before any AWS client is created; a missing file is "CSV file not found."
