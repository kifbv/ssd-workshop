- **(2.3) Address scan:** every text file (`.html .css .js .json .md .txt .svg`), Markdown and comments included, line by line (lines split at `\r\n`, `\r` or `\n`), reporting file and 1-based line. Refused: any `name://` (or `name:\\`) address whatever the scheme; `http`, `https`, `ws`, `wss` or `ftp` followed by `:` and more text even without slashes (`http:host`; `{ http: 1 }` and `"https:"` pass); two or more slashes or backslashes in any mix followed by a host character, after a quote or backtick, `url(`, `=` (any attribute, a meta refresh's `url=`), a comma (later `srcset` entries) or a meta refresh's delay without `url=` (`content="0; //host"`, `"0 //host"`, `"0,//host"`), with spaces or control characters allowed between. Each line is read three ways and the first reading with a finding is reported: as written; with HTML entities (numeric, leading zeros included as in `&#0000047;` and `&#x00002f;`, and named `&colon; &sol; &bsol; &Tab; ...`) and JavaScript/JSON escapes (`\/`, `\u002f`, `\u{2f}` with any leading zeros, `\x2f`, legacy octal `\57`, and the control escapes `\t \n \r \v \f \b` as the real characters) decoded; with entities and CSS escapes (`\2f `, `\/`) decoded; tabs and line breaks dropped in all three (browsers drop them in addresses). Every reading applies to every text file, so a style block or script inside HTML is covered. `//` followed by a space or `*` (a comment) or in plain code (`a // b`) is not an address. Images and fonts are not scanned. The template's own Markdown therefore names no such address (the allowed namespace names excepted).
- **(2.3) Limits of the scan:** an address built from parts at run time (`location.protocol + "//host"`, `"/" + "/host"`, `atob(...)`) or split over lines cannot be found by a scan; the apps' CSP (below) blocks loading from it. Links (`<a href>` navigation) are not covered by the CSP, so only the scan guards those. A JavaScript comment right after a closing quote with no space (`'x'//note`) fails: telling it from an opening quote needs a tokenizer, and a quote count would open holes (template literals, escaped quotes); AGENTS.md says to start comments with `// `.
- **(2.3) Text must be UTF-8:** a text file that is not valid UTF-8 (`TextDecoder("utf-8", { fatal: true })`), starts with a UTF-16 byte order mark or holds a NUL byte fails with "It is not plain UTF-8 text, so it cannot be checked." (another encoding would hide addresses from the scan). A UTF-8 byte order mark is fine.

- **(2.4) Sizes:** 100 KB = 102,400 bytes and 1 MB = 1,048,576 bytes, counted as the UTF-8 bytes of each value's canonical JSON (`JSON.stringify` of the parsed body; keys and item overhead do not count). The body is refused with 413 before parsing when it is over 100 KB (over 136,536 characters when base64), and again when its canonical form is (e.g. `1e20` written out).
- **(2.4) Nesting:** at most 100 levels of lists and objects (counted on the text, without recursion), 400 "This value is nested too deeply: lists and objects can go at most 100 levels deep."; deeper values overflow the stack when written out, a failure that depends on the runtime.
- **(2.4) `null` can be stored:** `PUT null` stores the value `null` and takes a key; `GET` answers `null` for it and for a missing key alike. Invalid or missing JSON answers 400 "Send the value as JSON."; a `PUT` without `content-type: application/json` answers 415 (the shared message).
- **(2.4) Answers:** `PUT` and `DELETE` answer 204 without a body; `GET` 200 with the stored JSON text; the preflight (`OPTIONS`, a route of its own, the HTTP API keeps no CORS configuration) 204 with `Access-Control-Allow-Methods: GET, PUT, DELETE`, `-Headers: content-type, accept`, `-Max-Age: 600`, without reading the table; every answer, errors and 404 included, carries `Access-Control-Allow-Origin: *` and `cache-control: no-store`, never `Access-Control-Allow-Credentials` and never a cookie. CloudFront's `/api/*` behaviour needed no change (all methods, managed `SecurityHeadersPolicy` without CORS).
- **(2.4) Limit reasons (413):** "This value is too big: a value can hold at most 100 KB.", "This app has no room left: an app can store at most 1 MB.", "This app already has 100 keys, the most it can keep. Remove one to add another." Replacing a value never counts as a new key, and a smaller value fits in a full app.
- **(2.4) Writes are atomic and race-safe:** a `PUT` or `DELETE` writes the value and the totals in one `TransactWriteItems`, only while the key's size in the totals item is still the one that was read (since try 3, see "Writes never read the value item"; `attribute_not_exists` for a new key) and the totals stay within the limits: `bytes <= 1 MB - change` and `keys <= 100 - new key`, so parallel writes can never pass the limits (tested with 130 parallel writes on the fake, and the conditions on the DynamoDB request). A lost race (a value or totals condition, or `TransactionConflict`) reads again and tries again after a random 20 to 80 ms pause (every write of an app updates the same `DATA_USAGE` item, so simultaneous writes, such as the template's shared counter pressed by several visitors, cancel each other with `TransactionConflict` on DynamoDB, and an immediate retry would collide again), 4 tries in all (try 1 had 3 without a pause), then answers 409 "This value was being changed by someone else at the same moment. Please try again."; a real limit found on the new read answers 413. Two writes of the same size to one key both succeed (last write wins): the totals stay right because they depend only on sizes.
- **(2.4) Logs:** one JSON line per request with method, outcome, status and the value's size; never the nickname, key, value, headers or event; failures log only the error name and answer 500 "The data service had a problem. Please try again in a moment."
- **(2.4) Daily write budget (try 2, after the access review; size and count changed in try 3):** replacing a value never meets the 1 MB or 100-key limits, so a loop of 100 KB `PUT`s on one key at the stage's 50 requests/s would cost hundreds of dollars a day in DynamoDB writes (about 2 write units per KB in a transaction). Each app may write 5 MB per UTC day (try 2: 20 MB), counted as DynamoDB bills it (try 3, `writeCost` in `platform/api/app-data/data.ts`): both items the transaction writes, each in whole KB at the larger of its old and new size (DynamoDB bills the larger), so the value item counts `max(bytes, previousBytes)` plus 256 bytes of item overhead, at least 1 KB (a `DELETE` counts the value it removes), and the totals item counts its own size (256 bytes plus each key's length and 8 bytes, ~7.3 KB with 100 keys of 64 characters). A small write counts 2 KB, a 100 KB one 102 KB, and the "PUT 100 KB, then PUT 1" trick counts 102 KB for each write (try 2 counted 1 KB for the second; tested). A `DELETE` of a missing key, reads and refused writes count nothing. 5 MB is about 2,500 small writes a day per app (a press of the template's counter is one), ample for a workshop app, while a loop of 100 KB writes stops after 50; at worst 30 live apps x 5 MB x 2 write units per KB is ~0.3 M write units a day, about $0.25 a day, ~$7 a month (on-demand eu-central-1 price assumed: $0.7625 per million write units). The count lives in the `DATA_USAGE` item (`writeDay` = UTC date YYYY-MM-DD, `writtenBytes`) and changes in the same `TransactWriteItems` as the value, so it is race-safe like the 1 MB limit: when the read showed writes of today, the update adds the cost with the condition `writeDay = :today AND writtenBytes <= budget - cost`; otherwise it sets `writeDay = :today, writtenBytes = cost` with the condition `attribute_not_exists(writeDay) OR writeDay < :today` (try 3; try 2 had `<>`; ISO dates compare as text): a write of today that got in first makes it a lost race, read again, and a stored day later than today (another instance's clock ahead) also fails the condition, so the count only moves forward and is never reset by a clock behind (tested; such a write answers 409 after its 4 tries, for the few moments the clocks differ). Over budget answers 429 "This app has saved a lot of data today. Saving starts again tomorrow." (outcome `write-budget`), storing nothing; reads keep working. The day turns at midnight UTC.
- **(2.4) Route throttles (try 2; writes raised in try 3):** instead of the stage's default 50 requests/s (burst 100), `PUT` and `DELETE /api/apps/{nickname}/data/{key}` get 30 requests/s (burst 60; try 2 had 10/20, reachable by a workshop room of ~30 people pressing shared counters) and `GET` 20/s (burst 40), as stage `RouteSettings` like the sign-in routes; `OPTIONS` also 20/s (burst 40) since the final access review (each preflight invokes the function; browsers keep the answer 600 s, so a real app sends few). The throttles are for the whole API (all apps together), the budget per app. A read is not much cheaper than a write per request: a `GET` of a 100 KB value costs 13 read units (eventually consistent, 4 KB per unit, half price) plus 1 for the live marker, ~$2 per million `GET`s, and ~100 KB of CloudFront egress (~$8.70 per million); a write refused with 429 costs 3 read units (live marker, totals item) and its API Gateway and Lambda requests. With the budget capping write units and a write reading only the small totals item, 30 writes/s is cheap; see "Remaining worst-case cost".
- **(2.4) Writes never read the value item (try 3, after the access re-review):** DynamoDB bills a `GetItem` on the whole item's size even with a `ProjectionExpression`, so try 2's consistent read of the value item (to learn its previous size) cost up to 25 read units on every `PUT` and `DELETE`, refused ones included, for a stranger who stored one 100 KB value. Each key's size now lives in the totals item's map `sizes` (`SET sizes.#k = :size`, `REMOVE sizes.#k`; the data key goes through `ExpressionAttributeNames`, as keys may hold dashes; IAM's `dynamodb:Attributes` holds only top-level names, so it sees `sizes`, per the DynamoDB guide). A write reads only the totals item (consistent, ≤ 2 read units) and checks the limits (413) and the budget (429) from it before anything else is read or written; the first write of an app creates the item with the map (`SET sizes = :sizes`, condition `attribute_not_exists(pk)`), since a nested `SET` on a missing map fails. The value item's own condition is dropped: the transaction's one condition is on the totals item (`sizes.#k = :previous`, or `attribute_exists(sizes) AND attribute_not_exists(sizes.#k)` for a new key, plus the limits and the budget), and since every change to a value changes its `sizes` entry in the same transaction, and transactions are serializable, the entry always holds the stored value's size: a write that read a stale size fails the condition, reads again and tries again, as before. Two writes of the same size to one key both succeed (last write wins), as before. No migration: items written by tries 1 and 2 never reached production (nothing was deployed).
- **(2.4) `GET` reads eventually consistently (try 3):** half the cost of a consistent read. A read right after a write may, rarely (typically for under a second), return the previous value; acceptable for apps. The template's counter reads only when the page loads, so a visitor would need to reload within that moment to see the previous count (a press then adds to it, and one press is lost); writes are unaffected (they read the totals item consistently). The live marker stays a consistent read (1 read unit).

Check the connection and try again." The edge stack has a behaviour `/api/apps/*`, before `/api/*`, identical to it (same origin, all methods, HTTPS only, CachingDisabled, AllViewerExceptHostHeader) but with a custom response headers policy `ssd-workshop-app-data-v1` (retained, versioned like the pages' policy; the deploy rights can create response headers policies) that keeps the managed SecurityHeadersPolicy's headers (HSTS one year, nosniff, `SAMEORIGIN`, XSS block, referrer, none overriding) and adds CORS: `Access-Control-Allow-Origin: *`, no credentials, methods `GET, PUT, DELETE`, headers `content-type, accept`, max age 600 (the function's preflight values), `originOverride: true` so the function's own header is replaced and an answer never carries it twice (CloudFront adds CORS headers to requests that send `Origin`, which every sandboxed fetch does: `Origin: null`). A throttled visitor then sees the API's own `message`: API Gateway's throttle body is `{"message":"Too Many Requests"}`, so "Too Many Requests"; without a readable body `workshop-data.js` shows "The data service answered with an error (429)." (`templates/basic/workshop-data.js` unchanged; to confirm after the deploy, infra/README.md).

- **(1.4) Code rate limit:** at most 5 codes per address in any sliding 60 minutes, kept in a `CODE_REQUESTS` item next to the code (`EMAIL#<email>`, `sentAt` epoch seconds of the window's sends, `version`, TTL `expiresAt` one hour after the newest send), so it outlives the 10-minute code. Only allow-listed addresses are ever written (no stranger's address is stored). A send is counted before it is made, so a failed send still uses one of the five; a refused (sixth) request is not recorded, so asking again does not extend the wait. Two requests at once: each write names the version it read (conditional `PutItem`), and the loser sends nothing.
- **(1.4) Code and its hash:** `crypto.randomInt(0, 1_000_000)`, zero-padded to six digits. Stored as `scrypt$<salt>$<hash>` (scrypt N=2^14, r=8, p=1, 16-byte random salt, 32-byte key); `verifyCode` (constant-time compare) is ready for 1.5. No secret pepper: that would need Secrets Manager or KMS, new paid services. Accepted risk: a 6-digit code's hash can be brute-forced from a leaked table (one million scrypt tries, hours of CPU), which matters little because a code lives 10 minutes and 1.5 burns it after 5 wrong tries.
- **(1.4) Codes item (a new code cancels none):** every unexpired code stays valid, so a stranger who knows a colleague's address cannot cancel the code they are typing. The `CODE` item holds `codes`, a list of at most 5 entries `{ codeHash, expiresAt }` (now + 600 s; expired entries pruned on each write), one `attempts` counter shared by all the codes (kept while earlier codes live, reset when none does), a `version` (conditional `PutItem`, re-read and retried at most 3 times on a conflict, then `conflict` and no send) and TTL `expiresAt` = the latest code's expiry. `verifyAnyCode` (for 1.5) checks every unexpired entry with no early exit. Remaining risk, accepted: someone could still use up a participant's 5 codes for the hour ahead of them; the participant can then use any of those 5 codes from their inbox, and a facilitator reset can come with the phase 3 dashboard.

- **(1.4) Fixed answer time:** a listed address does more work (scrypt, writes, SES) than one not on the list, so timing or a Lambda timeout (a 503 only listed addresses could reach) could reveal list membership. Every request that passes the syntax check therefore gets its neutral 202 exactly `ANSWER_AFTER_MS` = 3000 ms after the handler starts: the work races against that deadline, and work still running then is dropped (logged as `failed`, its step, `Timeout`); dropped work is frozen with the Lambda environment and may resume in the next request on that instance (a late email, no log line), while that next request's answer time is unaffected. SDK clients are bounded (`maxAttempts: 2`, `NodeHttpHandler` with `connectionTimeout` 1000 ms and `requestTimeout` 1500 ms, no proxy in Lambda), so a slow call fails rather than hangs. The `400` for malformed input is not padded: it depends only on the input's syntax, never on the list. Cost: 3 s of a 512 MB function per request (about $0.00002 on arm64), negligible at workshop volume. Tested with fake timers (listed, unlisted, rate-limited and failing requests answer at exactly 3000 ms; a mailer that never resolves still gets the 202 at the deadline; the 400 is immediate).
- **(1.4) Code route throttle:** `POST /api/sign-in/code` has its own throttle on the `$default` stage, 5 requests/s with a burst of 10 (`SIGN_IN_CODE_THROTTLE` in `infra/lib/api-stack.ts`, stage `RouteSettings`, tested), below the stage-wide 50/100: the route needs no sign-in and every well-formed request holds a Lambda for 3 s, so a flood at the stage limit would keep about 150 executions busy. The whole workshop is about 15 people; a throttled request gets API Gateway's 429, which does not depend on list membership. - **(1.5) One session check:** `platform/api/session/session.ts` `requireSession` reads the cookie from API Gateway's `cookies` list, hashes the token, reads `SESSION#<hash>` (consistent read), compares `expiresAt` with the clock (TTL deletes late), reads the participant's `PROFILE` and returns `{participant, role}`, or `401 {"message":"Please sign in."}` for no cookie, a malformed or unknown (forged) token, an expired session or a missing profile. A table error is a `500 {"message":"Something went wrong. Please try again in a moment."}`, not a 401 (a failure should not sign anyone out). The role comes from the profile, which is refreshed from the allow-list at each sign-in: a role change in the allow-list takes effect at the next sign-in.
- **(1.5) Session cookie:** `__Host-ssd_session=<token>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=28800` (the `__Host-` prefix makes browsers refuse it without Secure, with a Domain or another Path). Token: 32 bytes of `crypto.randomBytes`, base64url (43 characters). Stored only as SHA-256 hex in `SESSION#<hash>`/`SESSION` with `tokenHash`, `participantId`, `createdAt` and `expiresAt` (= sign-in + 28,800 s, also the TTL). A fast hash is right here, unlike the code's scrypt: the token holds 256 random bits, so a leaked hash cannot be reversed by guessing. Sessions last 8 hours from sign-in and are not extended by use; there is no sign-out route yet (a page cannot clear an HttpOnly cookie itself); one can come with the pages if needed.
- **(1.5) Code check rules:** the shared `attempts` counts wrong tries over all live codes of an address; the 5th wrong try deletes (burns) the whole `CODE` item, a match deletes it too (no code can be used twice), and an expired code (`expiresAt` <= now) never matches. Every wrong try is counted with one atomic UpdateItem `ADD attempts :one, version :one` (condition `attribute_exists(pk)`, `ReturnValues: UPDATED_NEW`), so parallel guesses are never lost to a race: a burst gets at most 4 refusals before the burn, and the add that returns `attempts` >= 5 deletes the item at the version it returned (if that delete loses a race, the item keeps `attempts` >= 5 and the next read burns it; reads always treat `attempts` >= 5 as burned). A wrong try on an item that vanished meanwhile is refused (`no-code`) and creates nothing. Using a matched code deletes `CODE` conditional on the `version` read; on a conflict the check reads again, at most 3 times, then refuses (`conflict`). Every write bumps or removes `version` (the code request writes `CODE` conditionally on it). A code is 6 ASCII digits after trimming; anything else is a malformed request.
- **(1.5) One refusal, one answer time:** an address not on the list (or whose entry lost its `email`), no live code, an expired, wrong or burned code, a lost race, a table failure and work still running at the deadline all get `401 {"message":"That code is not right or has expired. Ask for a new one."}`, and every well-formed request (success included) is answered exactly `ANSWER_AFTER_MS` = 3000 ms after the handler starts, with the bounded SDK clients of 1.4 (now shared in `platform/api/aws.ts`), tested with fake timers. Malformed input gets `400 {"message":"Send a JSON body with your email address and the 6-digit code."}` and a missing or other content type `415`, both at once and never echoing the input (they depend only on syntax). If the work runs out of time after using the code, the person asks for a new one (rare; accepted).
- **(1.5) JSON content type required on writes:** `POST /api/sign-in/verify` and `POST /api/me/nickname` need `content-type: application/json` (parameters allowed), else `415 {"message":"Send the request as JSON (content-type: application/json)."}`: a cross-site form cannot send that type without a CORS preflight, which the API never grants, on top of SameSite=Strict. The 1.4 code route is unchanged (it sets no cookie and acts on no session).
- **(1.5) Participant record:** on the first successful sign-in the function makes a random UUID (`newParticipantId` in `keys.ts`), links it from the allow-list entry with an UpdateItem of `participantId` only (conditional on the entry existing and having no link, so the import's fields stay and two first sign-ins at once end on one participant), then upserts `PARTICIPANT#<id>`/`PROFILE` with `type`, `id`, `role` and `group` from the entry, `createdAt` and `step` (`nickname`) only if new (`if_not_exists`), `ReturnValues: UPDATED_NEW`. A returning person reuses the linked participant, with role and group refreshed. The allow-list import keeps `participantId` on re-import (its UpdateItem never names it; tested in `platform/src/allowlist/store.test.ts`). No email in the profile, the session, any answer or log.
- **(1.5) Where to go after sign-in:** verify answers `200 {"next":"<step>"}` with the cookie: `nickname` for a new person (or one who never picked one), otherwise the step they are at.
- **(1.5) Nickname rules:** `^[A-Za-z0-9-]{3,20}$` after trimming spaces, then a reserved list compared in lower case (`RESERVED_NICKNAMES` in `platform/api/participant/participant.ts`): admin, administrator, api, apps, assets, claude, facilitator, facilitators, globe, help, intro, login, logout, me, null, root, sign-in, sign-out, signin, static, support, system, undefined, workshop, www, x (site paths and names that could pass for staff or the system). Please pick another one.", `409 {"reason":"taken"}` "That nickname is already taken. Please pick another one."; a body without a string `nickname` gets `400`. A saved nickname answers `200` with the record (step `clarify`).
- **(1.5) Nickname uniqueness:** a `NICK#<lower-case nickname>`/`NICK` claim (`type`, `nickname` as typed, `participantId`, `createdAt`) is put with `attribute_not_exists(pk)` in one `TransactWriteItems` with the profile update (`SET nickname, step = clarify` if the profile exists, has no nickname and is at step `nickname`). A cancelled claim is `taken`; a cancelled profile update is `already-set`.

- **(1.5) Own record only:** `GET /api/participants/{id}` answers the caller's own record for their own id; any other id, existing or not, gets the same `404 {"message":"Not found."}` without reading it, for every role (facilitator views of others come in phase 3).
- **(1.5) Sign-in verify function:** `ssd-workshop-api-sign-in-verify` (Node.js 22, arm64, 512 MB for scrypt, 10 s), own role and log group; rights: its logs; `dynamodb:GetItem` in `EMAIL#*`; `dynamodb:UpdateItem` in `EMAIL#*` with `dynamodb:Attributes` `pk`, `sk`, `attempts`, `version`, `participantId`; `dynamodb:DeleteItem` in `EMAIL#*`; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `pk`, `sk`, `type`, `id`, `role`, `group`, `step`, `createdAt` (never `nickname`); `dynamodb:PutItem` in `SESSION#*` with the session's attribute names (lists in `infra/lib/config.ts`, tested against the store's writes). It cannot write `email`, `role` or `group` of an allow-list entry, so it cannot add anyone to the list or change a listed person's role or group there. By design (this is the sign-in) it can write `role` and `group` on any `PARTICIPANT#*` profile and create a session for any participant id. Residual risks, accepted like 1.4's: code running as this role (a bug or a compromised function) could give any profile any role, sign in as anyone by putting a session, delete an `ALLOW` entry or point another entry's `participantId` elsewhere (IAM has no sort-key condition, and an attribute list on DeleteItem would not prevent it); the shipped code takes role and group only from the allow-list entry, puts a session only after a matched code, deletes only `CODE` items at a version it read or was returned, and links only an entry with no link. - **(1.5) Profile step after sign-in:** the profile upsert keeps `ReturnValues: UPDATED_NEW` (`SET step = if_not_exists(step, :first)` counts as an update of `step`, so it comes back even when unchanged). Not `ALL_NEW`: it would return `nickname` and any other attribute outside the role's `dynamodb:Attributes` list (AWS pairs such a list with `ReturnValues` `NONE`, `UPDATED_OLD` or `UPDATED_NEW`). If `step` is ever missing or unknown in the answer, the sign-in still succeeds with `{"next":"nickname"}` instead of failing; the live check in `infra/README.md` proves a returning person gets `{"next":"clarify"}`.
- **(1.5) Participant function:** `ssd-workshop-api-participant` (Node.js 22, arm64, 256 MB, 10 s), own role and log group; rights: its logs; `dynamodb:GetItem` in `SESSION#*` and `PARTICIPANT#*`; `dynamodb:PutItem` in `NICK#*` with the claim's attribute names; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `pk`, `sk`, `nickname`, `step` only (a transaction is authorized item by item; there is no `TransactWriteItems` action). - **(1.7) Hand-off through a queue (SQS approved by Franck, 2026-11-23, as a new paid service at about $0 a month):** the conversation function cannot invoke the worker (the boundary has no `lambda:InvokeFunction`, and invoke permissions for other principals are denied), so a stored message goes to the SQS queue `ssd-workshop-ai-messages` (SQS-managed encryption, 1 day retention) and an event source mapping (batch size 1) runs `ssd-workshop-api-ai-worker`. - **(1.7) Queue timings:** worker timeout 300 s; visibility timeout 330 s (just above the timeout, not AWS's six times: with batch size 1 a longer one only delays the retry past the stale limit), so SQS delivers a crashed job again about 5.5 minutes later while its message is still pending; a job whose worker crashed 3 times goes to `ssd-workshop-ai-messages-dlq` (14 days). The last run starts by about 660 s and ends by about 960 s, within `STALE_PENDING_SECONDS` = 1200 s (20 minutes, was 10; `infra/lib/app.test.ts` checks the sum). The AI calls are cut off 30 s before the Lambda timeout (`WRITE_RESERVE_MS`), which leaves time for the final write and its retries. Risk: the worker has no reserved concurrency in the shared account, and a throttled invoke still uses up a receive, so in a burst at the account's Lambda limit a job could reach the dead-letter queue; the participant then sees "failed" and can send again.
- **(1.7) At most 5 workers at once:** `maxConcurrency` 5 on the SQS event source (AWS's minimum is 2), so a burst of messages waits in the queue (without using up receives) instead of hitting Bedrock throttling; a message waiting there still counts towards the 20-minute stale limit, which leaves about 4 minutes of slack.
- **(1.7) Failures and retries:** a Bedrock error (after the SDK's 3 attempts with backoff), the deadline, an empty answer or a failed history read ends the message as `failed` at once with "Sorry, something went wrong. Please send your message again." and frees the conversation (no SQS retry, which would wait for the visibility timeout). The final write is tried 3 times (`FINISH_ATTEMPTS`, waits of 200 ms and 800 ms; a lost race is not retried); if the last try fails, the tokens already spent are added to `USAGE` on their own (one `ADD`; its own failure is ignored) and the error is thrown, so SQS delivers the job again; a failed read of the message is thrown too. A redelivered job runs from the start, and its Bedrock calls are counted again (they are spent too). The handler logs a thrown error as `{"event":"ai-worker","outcome":"error","error":<name>}` and throws a bare `Error("job failed")`, so the Lambda runtime never writes the original message or stack to CloudWatch. A pending message older than 20 minutes (`STALE_PENDING_SECONDS`, only a job that crashed 3 times or waited long in the queue leaves one) is shown as `failed` and no longer blocks a new message; its late job is skipped.
- **(1.7) Idempotent worker:** the worker skips a job whose message is not `pending` (or is stale), and stores the outcome in one `TransactWriteItems`: the message's status (condition: still `pending`), the reply (condition: none yet), the conversation (condition: this message is still in flight) and the usage `ADD`. A job delivered twice is therefore answered and counted once (two Bedrock calls at most, if both deliveries run at the same moment).
- **(1.7) Conversation items:** participant messages at `PARTICIPANT#<id>`/`MSG#<message id>` (`type`, `author`, `step`, `text`, `status` pending/done/declined/flagged/failed, `createdAt`, `pendingSince`, after an approval `approvedTextHash`, then the guardrail's `verdict`, `verdictReason`, `suggestion` and `guardrail*` tokens and cost); the reply at `MSG#<message id>-r`, which sorts right after its message (`kind` answer/decline/failure, `text`, `replyTo`, and for answers `prompt`, `modelId`, `promptVersion`, `historyCount`, `inputTokens`, `outputTokens`, `costUsd`); ids and the participant id are read from the keys, not stored twice. On path: describing or refining a small single-page app idea (trackers, calculators, lists, quizzes, simple games, small dashboards over data the participant types in), answering the assistant, asking about the workshop or for explanations. Flag: medical, mental-health, legal or financial advice, external paid APIs or keys, payments, minors or real names, or anything uncertain. Any other answer (no JSON, unknown verdict) is a flag.
