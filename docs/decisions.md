# Decisions

Choices made while building that the specification left open. Newest phase first.

## How changes are made

- **Spec signed off (2026-11-22):** [AI Workshop Platform: Spec](https://claude.ai/artifact/6mNkKPKQysWNoj7eL6Gyus), signed off by Franck, all 23 confirm-or-correct points confirmed.
- **Workflow:** each phase starts with a brief in `docs/phases/` and one round of questions.
  During a ticket, choices that can be undone are decided, recorded here and listed for veto in
  the pull request; only the cases under "Stop and ask" in `CLAUDE.md` wait for Franck. Each
  ticket is built in fresh-session tries and judged by the `checker` agent, at most 3 tries.
- **Spec deltas:** a change to signed-off behaviour is recorded here as ADDED, CHANGED or REMOVED,
  with the date and the pull request.

- **(1.1) API stack:** `ssd-workshop-api` (eu-central-1, `infra/lib/api-stack.ts`) holds the table, the HTTP API and its Lambda functions; it uses the assets-bucket synthesizer (the Lambda code is a file asset) and deploys after `ssd-workshop-cdk-assets`. If the first deploy of `ssd-workshop-api` fails and rolls back, the table stays behind outside any stack (retain plus deletion protection; resource import is denied), and every later deploy fails on its name: Franck removes the empty table by hand (`infra/README.md`, "If the first API deploy fails").
- **(1.1) Key scheme:** `EMAIL#<email>` + `ALLOW` / `CODE` (and `CODE_REQUESTS` from 1.4), `SESSION#<token hash>` + `SESSION`, `PARTICIPANT#<id>` + `PROFILE` / `MSG#<message id>` / `USAGE`, documented in `platform/api/types.ts` and built only by `platform/api/keys.ts` (tested: emails trimmed and lower-cased, ids without `#`, no email in error messages). A participant's profile, messages and usage share one partition, so a read always names the caller's own id. Message ids start with the ISO creation time, so the conversation queries in order and one message is a direct GetItem. Later tickets add fields and item types (e.g. a nickname claim for uniqueness in 1.5).
- **(1.1) Usage:** running totals per participant in one `USAGE` item (tokens and US dollars); each assistant message also carries its own tokens and cost.

No access logging for now: the Lambda logs suffice, and stage access logs may need API Gateway's service-linked role, which the deploy rights create only for ECS (`iam:CreateServiceLinkedRole`); to be checked before a ticket turns them on.
- **(1.1) Health function:** `ssd-workshop-api-health`, Node.js 22, arm64, 256 MB, 10 seconds, its own role `ssd-workshop-api-health` (only `logs:CreateLogStream`/`PutLogEvents` on its log group, no managed policy) and its own log group `ssd-workshop-api-health` (two weeks, deleted with the stack). It answers 200 `{"ok":true}` with `content-type: application/json` and `cache-control: no-store`. The table name is not passed yet; the first function that reads the table gets it and its grant.

A test loads the bundled `index.js` and calls it.

- **(1.1) Health check after every deploy:** the deploy workflow reads `ssd-workshop-api`'s `ApiEndpoint` output (stack name from `config.ts` through `print-deploy-settings.ts`, `api_stack`) and requires `GET /api/health` to answer 200 `{"ok":true}`, five tries 10 seconds apart; the same command is in `infra/README.md`.
- **(1.2) `/api/*` behaviour:** CloudFront sends `/api/*` to the HTTP API's execute-api address (`HttpOrigin`, HTTPS only to the origin) with the managed `CachingDisabled` cache policy, the managed `AllViewerExceptHostHeader` origin request policy (cookies, query strings and every header except `Host`, which API Gateway needs as its own), all seven methods (`GET`, `HEAD`, `OPTIONS`, `PUT`, `PATCH`, `POST`, `DELETE`; the body passes through) and the managed `SecurityHeadersPolicy`, as on the pages. Managed policies only: no new untaggable CloudFront resource. Pages and API share one origin, so no CORS and no new DNS record.
- **(1.2) API id as a constant:** `API_ID = "ut2mzqmbb4"` and `API_ORIGIN_DOMAIN` in `infra/lib/config.ts`, because the edge stack (us-east-1) cannot read the api stack's output across regions (`crossRegionReferences` is not allowed). If `ssd-workshop-api` is ever recreated, the API gets a new id: update `API_ID` in the same pull request, or `/api/*` breaks (the post-deploy check through CloudFront then fails).
- **(1.2) HTTPS only for `/api/*`:** the viewer protocol policy is `https-only`, not `redirect-to-https` as for the pages: a redirect would turn a `POST` into a `GET` and lose its body. Plain HTTP to `/api/*` gets 403 from CloudFront.
- **(1.2) Zone diff in the deploy workflow:** before `cdk deploy`, the workflow saves the rankly.games zone (`aws route53 list-resource-record-sets`, zone id from `config.ts` through `print-deploy-settings.ts`, `hosted_zone_id`), sorted with `jq -S` by name, type and set identifier, to `$RUNNER_TEMP` (never committed); after the deploy it takes a second snapshot and fails with `::error::` if `diff` finds any change. The after-check also runs when the deploy failed (`!cancelled()`, as long as the first snapshot succeeded). A later ticket that changes the workshop record on purpose must adjust this check. On a change the log shows only the names and types of the changed records, never their values, because the zone also holds other projects' records. A change by another project during the deploy also fails the check; re-running the deploy clears it.
- **(1.2) Health check through CloudFront:** after every deploy, `GET https://workshop.rankly.games/api/health` must answer 200 with exactly `{"ok":true}`, ten tries 30 seconds apart (CloudFront can take minutes to roll out a behaviour). The direct execute-api check from 1.1 stays: it tells a broken API apart from a broken CloudFront route.
- **(1.2) Direct execute-api address stays reachable (Franck 2026-11-23):** the API's own address keeps answering next to `https://workshop.rankly.games/api/`. Accepted: every route checks the session itself and the stage is throttled. A secret origin header (CloudFront adds it, the API refuses requests without it) can follow as its own ticket.
- **(1.4) Code request answer:** every well-formed `POST /api/sign-in/code` gets `202`, headers `content-type: application/json` and `cache-control: no-store`, body `{"message":"If this address is on the workshop list, a sign-in code is on its way. It can take a minute; check your Junk folder too."}`: the same bytes, at the same time (see "Fixed answer time"), for a listed address, one not on the list, one over its hourly limit, a lost race, a table or SES failure and work still running at the deadline (tested).
- **(1.4) Code request failures:** a DynamoDB or SES error still gets the neutral answer (never a 500: an error that only listed addresses can reach would reveal who is on the list); the function logs one line with the failing step and the error's `name` only. An outage is therefore visible in the log group, not to the person, who can ask again.
- **(1.4) Malformed code request:** `400` with `{"message":"Send a JSON body with one email address."}`, never echoing the input, for a missing or non-JSON body (base64 bodies are decoded first), a body over 2 KB, JSON that is not an object, a missing or non-string `email`, an address over 320 characters or one the allow-list import would refuse. The check is syntactic only and says nothing about the list.
- **(1.4) One email rule:** the allow-list import's address rule moved to `platform/api/email.ts` (`isValidEmail`), used by the import, the code request and `smoke signin`, so every stored address passes at sign-in; `platform/src/allowlist/logic.ts` re-exports it.
- **(1.4) Code rate limit:** at most 5 codes per address in any sliding 60 minutes, kept in a `CODE_REQUESTS` item next to the code (`EMAIL#<email>`, `sentAt` epoch seconds of the window's sends, `version`, TTL `expiresAt` one hour after the newest send), so it outlives the 10-minute code. Only allow-listed addresses are ever written (no stranger's address is stored). A send is counted before it is made, so a failed send still uses one of the five; a refused (sixth) request is not recorded, so asking again does not extend the wait. Two requests at once: each write names the version it read (conditional `PutItem`), and the loser sends nothing.
- **(1.4) Code and its hash:** `crypto.randomInt(0, 1_000_000)`, zero-padded to six digits. Stored as `scrypt$<salt>$<hash>` (scrypt N=2^14, r=8, p=1, 16-byte random salt, 32-byte key); `verifyCode` (constant-time compare) is ready for 1.5. No secret pepper: that would need Secrets Manager or KMS, new paid services. Accepted risk: a 6-digit code's hash can be brute-forced from a leaked table (one million scrypt tries, hours of CPU), which matters little because a code lives 10 minutes and 1.5 burns it after 5 wrong tries.
- **(1.4) Codes item (a new code cancels none):** every unexpired code stays valid, so a stranger who knows a colleague's address cannot cancel the code they are typing. The `CODE` item holds `codes`, a list of at most 5 entries `{ codeHash, expiresAt }` (now + 600 s; expired entries pruned on each write), one `attempts` counter shared by all the codes (kept while earlier codes live, reset when none does), a `version` (conditional `PutItem`, re-read and retried at most 3 times on a conflict, then `conflict` and no send) and TTL `expiresAt` = the latest code's expiry. `verifyAnyCode` (for 1.5) checks every unexpired entry with no early exit. Remaining risk, accepted: someone could still use up a participant's 5 codes for the hour ahead of them; the participant can then use any of those 5 codes from their inbox, and a facilitator reset can come with the phase 3 dashboard.
- **(1.4) Code email wording:** subject "Your SSD Workshop sign-in code: 123456"; text and HTML say "Your SSD Workshop sign-in code is:", the code (large monospace in HTML), "Enter it on the sign-in page. The code is valid for 10 minutes.", "You get this email because someone asked to sign in to the SSD Workshop with this address. If it wasn't you, you can ignore this email." and "Questions? Ask your facilitator." From `"SSD Workshop" <ssd-workshop@rankly.games>`, configuration set `ssd-workshop-email`, no Reply-To, no images, no links, inline styles only.
- **(1.4) Code request logs:** one JSON line per request, `{"event":"sign-in-code","outcome":...}` with outcome `sent`, `not-listed`, `rate-limited`, `conflict`, `invalid-request` or `failed` (plus `step` and the error name, kept only if it looks like an identifier, or `Timeout` when the work was still running at the deadline; the dropped work then logs nothing more). The log type has no field for an address, a code or the body; a capture test proves none reaches `console` or stdout/stderr.
- **(1.4) API settings as constants:** `platform/api/settings.ts` holds region, table, sender, display name and configuration set as constants, not environment variables, so a function cannot be pointed elsewhere by configuration; a test checks them against `infra/lib/config.ts`.
- **(1.4) Sign-in code function:** `ssd-workshop-api-sign-in-code` (Node.js 22, arm64, 512 MB so scrypt runs at a predictable speed, 10 s timeout, well above the 3 s answer time), own role and log group; rights: its logs; `dynamodb:GetItem` with `ForAllValues:StringLike dynamodb:LeadingKeys ["EMAIL#*"]`; `dynamodb:PutItem` with the same condition plus `ForAllValues:StringEquals dynamodb:Attributes` = the CODE and CODE_REQUESTS attribute names (`pk`, `sk`, `type`, `codes`, `attempts`, `sentAt`, `version`, `expiresAt`; `SIGN_IN_CODE_PUT_ATTRIBUTES` in `infra/lib/config.ts`, tested against the store's writes); and `ses:SendEmail` on the two identities and the configuration set with `ses:FromAddress = ssd-workshop@rankly.games`. The function is reachable without sign-in, so it cannot read or write sessions, participants or messages. IAM has no condition on the sort key, so it could still put an `ALLOW` item, but not its `email` attribute: the allow-list check now requires `email` (only the import writes it). Residual risk, accepted for now: a PutItem replaces the whole item, so code running as this role could overwrite an existing `EMAIL#<x>/ALLOW` entry with only `pk`/`sk`/`type` and take that person off the list (denial of service; it can never add anyone or raise anyone's rights). The shipped code never does it, and IAM cannot condition on the sort key; moving codes to their own `CODE#` partition is the fix if it is ever needed. No access stack change (the boundary allows `dynamodb:*` on the table).
- **(1.4) AWS SDK bundled:** `NodejsFunction` leaves `@aws-sdk/*` out of the bundle by default on Node 18+ runtimes; `externalModules: []` bundles it (about 630 KB), so the function runs the SDK version the tests ran with and the synth test can load the bundle on its own.
- **(1.4) Fakes, not a mocking library:** the tests use in-memory fakes behind the small `SignInStore` and `CodeMailer` interfaces and stub clients for the DynamoDB and SES adapters; no `aws-sdk-client-mock` dependency.
- **(1.4) `smoke signin`:** `npm run -s smoke -- signin <address>` POSTs `{"email"}` to `https://workshop.rankly.games/api/sign-in/code` with Node's `fetch` (no AWS credentials), prints the masked address, the status and the answer (redacted, at most 500 characters), and exits 0 only on 202. The address is checked with the API's own rule first.
- **(1.4) Fixed answer time:** a listed address does more work (scrypt, writes, SES) than one not on the list, so timing or a Lambda timeout (a 503 only listed addresses could reach) could reveal list membership. Every request that passes the syntax check therefore gets its neutral 202 exactly `ANSWER_AFTER_MS` = 3000 ms after the handler starts: the work races against that deadline, and work still running then is dropped (logged as `failed`, its step, `Timeout`); dropped work is frozen with the Lambda environment and may resume in the next request on that instance (a late email, no log line), while that next request's answer time is unaffected. SDK clients are bounded (`maxAttempts: 2`, `NodeHttpHandler` with `connectionTimeout` 1000 ms and `requestTimeout` 1500 ms, no proxy in Lambda), so a slow call fails rather than hangs. The `400` for malformed input is not padded: it depends only on the input's syntax, never on the list. Cost: 3 s of a 512 MB function per request (about $0.00002 on arm64), negligible at workshop volume. Tested with fake timers (listed, unlisted, rate-limited and failing requests answer at exactly 3000 ms; a mailer that never resolves still gets the 202 at the deadline; the 400 is immediate).
- **(1.4) Code route throttle:** `POST /api/sign-in/code` has its own throttle on the `$default` stage, 5 requests/s with a burst of 10 (`SIGN_IN_CODE_THROTTLE` in `infra/lib/api-stack.ts`, stage `RouteSettings`, tested), below the stage-wide 50/100: the route needs no sign-in and every well-formed request holds a Lambda for 3 s, so a flood at the stage limit would keep about 150 executions busy. The whole workshop is about 15 people; a throttled request gets API Gateway's 429, which does not depend on list membership. Reserved concurrency was left out because it takes from the account-wide Lambda concurrency pool shared with other projects (Franck's call).
- **(1.4) Notes for 1.5:** verify must burn the whole `CODE` item after 5 wrong tries (shared `attempts`), delete it on success, check that the `ALLOW` entry (with its `email` attribute) still exists at verify time, and bump `version` on every write to the `CODE` item (the code request writes it conditionally on `version`). The sign-in page (1.6) shows a `429` from the code route as "Please try again in a moment", not as an error.
- **(1.5) Routes:** `POST /api/sign-in/verify` (no session; body `{"email","code"}`), and three protected routes served by one function `ssd-workshop-api-participant`: `GET /api/me` (own record `{"id","nickname" or null,"role","group","step"}`), `POST /api/me/nickname` (`{"nickname"}`) and `GET /api/participants/{id}`. All answers are JSON with `cache-control: no-store`.
- **(1.5) One session check:** `platform/api/session/session.ts` `requireSession` reads the cookie from API Gateway's `cookies` list, hashes the token, reads `SESSION#<hash>` (consistent read), compares `expiresAt` with the clock (TTL deletes late), reads the participant's `PROFILE` and returns `{participant, role}`, or `401 {"message":"Please sign in."}` for no cookie, a malformed or unknown (forged) token, an expired session or a missing profile. A table error is a `500 {"message":"Something went wrong. Please try again in a moment."}`, not a 401 (a failure should not sign anyone out). The role comes from the profile, which is refreshed from the allow-list at each sign-in: a role change in the allow-list takes effect at the next sign-in.
- **(1.5) Session cookie:** `__Host-ssd_session=<token>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=28800` (the `__Host-` prefix makes browsers refuse it without Secure, with a Domain or another Path). Token: 32 bytes of `crypto.randomBytes`, base64url (43 characters). Stored only as SHA-256 hex in `SESSION#<hash>`/`SESSION` with `tokenHash`, `participantId`, `createdAt` and `expiresAt` (= sign-in + 28,800 s, also the TTL). A fast hash is right here, unlike the code's scrypt: the token holds 256 random bits, so a leaked hash cannot be reversed by guessing. Sessions last 8 hours from sign-in and are not extended by use; there is no sign-out route yet (a page cannot clear an HttpOnly cookie itself); one can come with the pages if needed.
- **(1.5) Code check rules:** the shared `attempts` counts wrong tries over all live codes of an address; the 5th wrong try deletes (burns) the whole `CODE` item, a match deletes it too (no code can be used twice), and an expired code (`expiresAt` <= now) never matches. Every wrong try is counted with one atomic UpdateItem `ADD attempts :one, version :one` (condition `attribute_exists(pk)`, `ReturnValues: UPDATED_NEW`), so parallel guesses are never lost to a race: a burst gets at most 4 refusals before the burn, and the add that returns `attempts` >= 5 deletes the item at the version it returned (if that delete loses a race, the item keeps `attempts` >= 5 and the next read burns it; reads always treat `attempts` >= 5 as burned). A wrong try on an item that vanished meanwhile is refused (`no-code`) and creates nothing. Using a matched code deletes `CODE` conditional on the `version` read; on a conflict the check reads again, at most 3 times, then refuses (`conflict`). Every write bumps or removes `version` (the code request writes `CODE` conditionally on it). A code is 6 ASCII digits after trimming; anything else is a malformed request.
- **(1.5) One refusal, one answer time:** an address not on the list (or whose entry lost its `email`), no live code, an expired, wrong or burned code, a lost race, a table failure and work still running at the deadline all get `401 {"message":"That code is not right or has expired. Ask for a new one."}`, and every well-formed request (success included) is answered exactly `ANSWER_AFTER_MS` = 3000 ms after the handler starts, with the bounded SDK clients of 1.4 (now shared in `platform/api/aws.ts`), tested with fake timers. Malformed input gets `400 {"message":"Send a JSON body with your email address and the 6-digit code."}` and a missing or other content type `415`, both at once and never echoing the input (they depend only on syntax). If the work runs out of time after using the code, the person asks for a new one (rare; accepted).
- **(1.5) JSON content type required on writes:** `POST /api/sign-in/verify` and `POST /api/me/nickname` need `content-type: application/json` (parameters allowed), else `415 {"message":"Send the request as JSON (content-type: application/json)."}`: a cross-site form cannot send that type without a CORS preflight, which the API never grants, on top of SameSite=Strict. The 1.4 code route is unchanged (it sets no cookie and acts on no session).
- **(1.5) Participant record:** on the first successful sign-in the function makes a random UUID (`newParticipantId` in `keys.ts`), links it from the allow-list entry with an UpdateItem of `participantId` only (conditional on the entry existing and having no link, so the import's fields stay and two first sign-ins at once end on one participant), then upserts `PARTICIPANT#<id>`/`PROFILE` with `type`, `id`, `role` and `group` from the entry, `createdAt` and `step` (`nickname`) only if new (`if_not_exists`), `ReturnValues: UPDATED_NEW`. A returning person reuses the linked participant, with role and group refreshed. The allow-list import keeps `participantId` on re-import (its UpdateItem never names it; tested in `platform/src/allowlist/store.test.ts`). No email in the profile, the session, any answer or log.
- **(1.5) Where to go after sign-in:** verify answers `200 {"next":"<step>"}` with the cookie: `nickname` for a new person (or one who never picked one), otherwise the step they are at.
- **(1.5) Nickname rules:** `^[A-Za-z0-9-]{3,20}$` after trimming spaces, then a reserved list compared in lower case (`RESERVED_NICKNAMES` in `platform/api/participant/participant.ts`): admin, administrator, api, apps, assets, claude, facilitator, facilitators, globe, help, intro, login, logout, me, null, root, sign-in, sign-out, signin, static, support, system, undefined, workshop, www, x (site paths and names that could pass for staff or the system). Refusals have distinct reasons: `400 {"reason":"rules"}` "A nickname has 3 to 20 letters, digits or dashes.", `400 {"reason":"reserved"}` "That nickname is reserved. Please pick another one.", `409 {"reason":"taken"}` "That nickname is already taken. Please pick another one."; a body without a string `nickname` gets `400`. A saved nickname answers `200` with the record (step `clarify`).
- **(1.5) Nickname uniqueness:** a `NICK#<lower-case nickname>`/`NICK` claim (`type`, `nickname` as typed, `participantId`, `createdAt`) is put with `attribute_not_exists(pk)` in one `TransactWriteItems` with the profile update (`SET nickname, step = clarify` if the profile exists, has no nickname and is at step `nickname`). A cancelled claim is `taken`; a cancelled profile update is `already-set`.
- **(1.5) Nickname set once:** a second attempt gets `409 {"reason":"already-set","message":"You already have a nickname, and it can't be changed."}`. Changing it later (and freeing the old claim) can come with the facilitator dashboard if needed.
- **(1.5) Own record only:** `GET /api/participants/{id}` answers the caller's own record for their own id; any other id, existing or not, gets the same `404 {"message":"Not found."}` without reading it, for every role (facilitator views of others come in phase 3).
- **(1.5) Sign-in verify function:** `ssd-workshop-api-sign-in-verify` (Node.js 22, arm64, 512 MB for scrypt, 10 s), own role and log group; rights: its logs; `dynamodb:GetItem` in `EMAIL#*`; `dynamodb:UpdateItem` in `EMAIL#*` with `dynamodb:Attributes` `pk`, `sk`, `attempts`, `version`, `participantId`; `dynamodb:DeleteItem` in `EMAIL#*`; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `pk`, `sk`, `type`, `id`, `role`, `group`, `step`, `createdAt` (never `nickname`); `dynamodb:PutItem` in `SESSION#*` with the session's attribute names (lists in `infra/lib/config.ts`, tested against the store's writes). It cannot write `email`, `role` or `group` of an allow-list entry, so it cannot add anyone to the list or change a listed person's role or group there. By design (this is the sign-in) it can write `role` and `group` on any `PARTICIPANT#*` profile and create a session for any participant id. Residual risks, accepted like 1.4's: code running as this role (a bug or a compromised function) could give any profile any role, sign in as anyone by putting a session, delete an `ALLOW` entry or point another entry's `participantId` elsewhere (IAM has no sort-key condition, and an attribute list on DeleteItem would not prevent it); the shipped code takes role and group only from the allow-list entry, puts a session only after a matched code, deletes only `CODE` items at a version it read or was returned, and links only an entry with no link. The fix if ever needed is the same: codes in their own `CODE#` partition. Route throttle like the code route: 5 requests/s, burst 10 (`SIGN_IN_VERIFY_THROTTLE`).
- **(1.5) Profile step after sign-in:** the profile upsert keeps `ReturnValues: UPDATED_NEW` (`SET step = if_not_exists(step, :first)` counts as an update of `step`, so it comes back even when unchanged). Not `ALL_NEW`: it would return `nickname` and any other attribute outside the role's `dynamodb:Attributes` list (AWS pairs such a list with `ReturnValues` `NONE`, `UPDATED_OLD` or `UPDATED_NEW`). If `step` is ever missing or unknown in the answer, the sign-in still succeeds with `{"next":"nickname"}` instead of failing; the live check in `infra/README.md` proves a returning person gets `{"next":"clarify"}`.
- **(1.5) Participant function:** `ssd-workshop-api-participant` (Node.js 22, arm64, 256 MB, 10 s), own role and log group; rights: its logs; `dynamodb:GetItem` in `SESSION#*` and `PARTICIPANT#*`; `dynamodb:PutItem` in `NICK#*` with the claim's attribute names; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `pk`, `sk`, `nickname`, `step` only (a transaction is authorized item by item; there is no `TransactWriteItems` action). It cannot create sessions or touch the allow-list. One Lambda permission scoped to this API (`<api id>/*/*/*`, `scopePermissionToRoute: false`) instead of one per route, because CDK writes the `{id}` path parameter literally into the per-route source ARN (whether API Gateway's invoke ARN would match it is unverified until a deployed request proves it). No access stack change: the boundary already allows `dynamodb:*` on `table/ssd-workshop-*`, and the deploy rights already create functions, roles and routes.
- **(1.5) Accepted risk, codes burned by a stranger:** anyone who knows a listed address can burn that person's live codes with 5 wrong guesses (the spec's burn rule) and, with the 1.4 limit of 5 codes per hour, keep them out for about an hour; the answers reveal no membership. Accepted for a ~15-person workshop; a facilitator reset comes with the phase 3 dashboard.
- **(1.5) Accepted risk, sessions not re-checked:** a session is not re-checked against the allow-list, so a removed or demoted person keeps their session and role for up to 8 hours, and there is no sign-out route. Harmless in phase 1 (every role sees only its own record); must be revisited before phase 3 gives roles views of others.
- **(1.5) Notes for 1.6:** the verify route is throttled too (5 requests/s, burst 10), so the sign-in page shows a `429` from `POST /api/sign-in/verify` as "Please try again in a moment", not as an error (like the code route's). - **(1.7) Hand-off through a queue:** the conversation function cannot invoke the worker (the boundary has no `lambda:InvokeFunction`, and invoke permissions for other principals are denied), so a stored message goes to the SQS queue `ssd-workshop-ai-messages` (SQS-managed encryption, 1 day retention) and an event source mapping (batch size 1) runs `ssd-workshop-api-ai-worker`. The queue message holds only `{"participantId","messageId"}`, never the text. No queue policy (identity-based rights only; `sqs:AddPermission` is denied). No access stack change: the boundary and deploy rights already cover `sqs:*` on `ssd-workshop-*`, event source mappings of `ssd-workshop-*` functions and their tags, and `bedrock:InvokeModel` on `eu.anthropic.*` profiles and `anthropic.*` models.
- **(1.7) Queue timings:** worker timeout 300 s; visibility timeout 1800 s (six times the timeout, as AWS recommends for a Lambda source); a job whose worker crashed 3 times goes to `ssd-workshop-ai-messages-dlq` (14 days). The AI calls are cut off 30 s before the Lambda timeout (`WRITE_RESERVE_MS`), so the worker practically always stores an outcome.
- **(1.7) Failures and retries:** a Bedrock error (after the SDK's 3 attempts with backoff), the deadline, an empty answer or a failed history read ends the message as `failed` at once with "Sorry, something went wrong. Please send your message again." and frees the conversation (no SQS retry, which would wait for the 30-minute visibility timeout); a failed read of the message or a failed final write is thrown, so SQS delivers the job again. A pending message older than 10 minutes (`STALE_PENDING_SECONDS`, only a crashed worker leaves one) is shown as `failed` and no longer blocks a new message; its late job is skipped.
- **(1.7) Idempotent worker:** the worker skips a job whose message is not `pending` (or is stale), and stores the outcome in one `TransactWriteItems`: the message's status (condition: still `pending`), the reply (condition: none yet), the conversation (condition: this message is still in flight) and the usage `ADD`. A job delivered twice is therefore answered and counted once (two Bedrock calls at most, if both deliveries run at the same moment).
- **(1.7) Conversation items:** participant messages at `PARTICIPANT#<id>`/`MSG#<message id>` (`type`, `author`, `step`, `text`, `status` pending/done/declined/flagged/failed, `createdAt`, `pendingSince`, then the guardrail's `verdict`, `verdictReason`, `suggestion` and `guardrail*` tokens and cost); the reply at `MSG#<message id>-r`, which sorts right after its message (`kind` answer/decline/failure, `text`, `replyTo`, and for answers `prompt`, `modelId`, `promptVersion`, `historyCount`, `inputTokens`, `outputTokens`, `costUsd`); ids and the participant id are read from the keys, not stored twice. The conversation state is its own `CONVERSATION` item (`state` open/waiting, `pendingId`, `pendingSince`, `updatedAt`) rather than attributes of `PROFILE`: the roles that write the profile (sign-in, nickname) keep their attribute lists unchanged, and the one-message-in-flight rule is one conditional update on it. `types.ts` documents the shapes.
- **(1.7) Message ids:** the ISO creation time, a dash and 16 hex digits from 8 random bytes (`newMessageId`, no new dependency), e.g. `2026-11-23T10:00:00.000Z-1f2e...`; the poll route accepts only that pattern (`MESSAGE_ID_PATTERN`), so a reply id or any other sort key is never looked up.
- **(1.7) Routes:** `POST /api/conversation/messages` `{"text"}` (JSON content type, else 415; 1 to 2000 Unicode characters after trimming, body up to 16 KB, else `400 {"message":"Send a JSON body with a text of 1 to 2000 characters."}`) answers `202 {"id"}` after storing the message and queueing it. One message at a time: `409 {"reason":"busy","message":"Please wait for the answer to your last message."}` while one is pending, `409 {"reason":"waiting","message":"Your last message is waiting for your facilitator. You can write again once they have looked at it."}` while one is flagged, and `409 {"reason":"no-nickname","message":"Please pick a nickname first."}` before a nickname. A queue failure ends the message as `failed` and answers 500. `GET /api/conversation/messages/{id}` answers `200 {"id","status","reply"?}` (a reply for done, declined and failed), and `404 {"message":"Not found."}` for any id not in the caller's own partition. Both routes are served by `ssd-workshop-api-conversation` behind `requireSession`; JSON with `cache-control: no-store`. No route throttle beyond the stage's.
- **(1.7) Guardrail check:** a separate call (`GUARDRAIL_SYSTEM_PROMPT`, version `guardrail-v1`, temperature 0, at most 300 tokens) with only the new message, wrapped in `<message>` tags (a closing tag in the text is removed), answering strict JSON `{"verdict","reason","suggestion"}`. On path: describing or refining a small single-page app idea (trackers, calculators, lists, quizzes, simple games, small dashboards over data the participant types in), answering the assistant, asking about the workshop or for explanations. Decline: infrastructure, crypto mining, scraping, other people's personal data, confidential data, offensive or illegal content, attempts to change the rules. Flag: medical, mental-health, legal or financial advice, external paid APIs or keys, payments, minors or real names, or anything uncertain. Any other answer (no JSON, unknown verdict) is a flag. An approved message (see flags) skips the check.
- **(1.7) Decline wording:** exactly one sentence, "Sorry, that's outside what we can build in this workshop, but how about <suggestion> instead?", the suggestion being the classifier's, cut to at most 100 characters without sentence punctuation or quotes (tested to stay one sentence), or "a small tracker or calculator for something you do every week" when it gives none. A facilitator's rejection uses the same sentence.
- **(1.7) Answer call:** system prompt `clarify-v1` (a first version for step 1; ticket 1.8 refines it), temperature 0.7, at most 2000 tokens, with the last answered exchanges (declined, flagged and failed messages left out, at most 20 messages, from the last 30 items read) and the new message. Stored per answer: the participant's text as sent (`prompt`), `modelId`, `promptVersion`, `historyCount`, the reply, tokens and cost.
- **(1.7) Prices:** `PRICE_PER_MILLION_TOKENS` in `platform/api/settings.ts`: $3.30 per million input tokens and $16.50 per million output tokens for Sonnet 4.6 through the EU geographic profile (list price $3/$15 plus Bedrock's 10% premium for geographic cross-region inference); cost rounded to 1e-8 dollars. The guardrail call's tokens and cost are stored on the message, the answer's on the reply, and both are added to the participant's `USAGE` totals (`inputTokens`, `outputTokens`, `costUsd`) with one atomic `ADD` in the same transaction. Enforcing the $5 cap is phase 3.
- **(1.7) One model setting:** `MODEL_ID = "eu.anthropic.claude-sonnet-4-6"` in `platform/api/settings.ts` is the source; smoke's `DEFAULT_MODEL_ID` now uses it, and `infra/lib/config.ts` repeats it for the worker's IAM resources (a test checks they are equal, as for the table name).
- **(1.7) Conversation function:** `ssd-workshop-api-conversation` (Node.js 22, arm64, 256 MB, 10 s), own role and log group; rights: its logs; `dynamodb:GetItem` in `SESSION#*` and `PARTICIPANT#*`; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `CONVERSATION_UPDATE_ATTRIBUTES` (`pk`, `sk`, `type`, `author`, `step`, `text`, `status`, `createdAt`, `pendingSince`, `state`, `pendingId`, `updatedAt`, `kind`, `replyTo`); `sqs:SendMessage` on the queue. One Lambda permission scoped to this API (`scopePermissionToRoute: false`, path parameter route).
- **(1.7) AI worker:** `ssd-workshop-api-ai-worker` (Node.js 22, arm64, 256 MB, 300 s), own role and log group, no route; rights: its logs; `dynamodb:GetItem` and `dynamodb:Query` in `PARTICIPANT#*`; `dynamodb:UpdateItem` in `PARTICIPANT#*` with `AI_WORKER_UPDATE_ATTRIBUTES` (the message, reply, conversation and usage attributes; never `step`, `role`, `group`, `nickname`, `id` or `approved`); `bedrock:InvokeModel` on `inference-profile/eu.anthropic.claude-sonnet-4-6` in eu-central-1 and `arn:aws:bedrock:eu-*::foundation-model/anthropic.claude-sonnet-4-6` (the EU profile routes to the model in several EU regions); the consume rights on its queue (CDK's `SqsEventSource` grant). Bedrock client: 3 attempts, 3 s to connect, 120 s per request, plus the job's deadline.
- **(1.7) Updates only, `approved` written by nobody but the facilitator:** both functions write with `UpdateItem` (inside transactions), never `PutItem`, so they cannot replace or empty another item of a participant partition. Neither role may write `approved`, the marker that skips the guardrail, so only `npm run flags -- approve` (Franck's credentials) can set it. Residual risk, accepted like 1.4's and 1.5's: code running as either role could change the listed attributes on any item of any participant partition (e.g. a profile's `type`, or the conversation function's `step`), or fake a reply; it can never change a role, group or nickname, read emails or skip the guardrail.
- **(1.7) `npm run flags -- list | approve <nickname> | reject <nickname>`:** root script `npm run -s flags -w platform --` (`platform/src/flags/`: `command.ts` tested against the in-memory fakes, `store.ts`, `main.ts`), run with the owner's own credentials. The nickname (any letter case) is resolved through its `NICK#` claim. `list` prints "Waiting for a decision: N" and the nicknames (alphabetical, a paginated `Scan` of `CONVERSATION` items in state `waiting`); `approve` sets the flagged message back to `pending` with `approved = true` and the conversation to `open` (one transaction, conditional on it still being flagged and waiting), then queues it, and the worker answers it without a new check; `reject` declines it with the one-sentence decline and frees the conversation. Exit 1 for an unknown nickname, nothing waiting, a decision made meanwhile, or an AWS error (printed through `redactError`). Only nicknames and counts are printed, never a message text, an id or an email.
- **(1.7) `npm run eval -- guardrails`:** root script `npm run -s eval -w platform --` (`platform/src/eval/`: `logic.ts` with the suite switch, the file check and the scoring, tested with a fake classifier; `main.ts` calls Bedrock with the caller's credentials, `maxAttempts` 4). - **(1.7) Logs:** one JSON line per request, `{"event":"conversation","route":"send"|"poll"|"unknown","outcome":...}` (`accepted`, `ok`, `unauthorized`, `not-found`, `invalid-request`, `unsupported-media-type`, `busy`, `waiting`, `no-nickname`, `failed` with the error name), and one per job, `{"event":"ai-worker","outcome":...,"verdict"?,"error"?}` (`done`, `declined`, `flagged`, `failed`, `skipped`, `invalid`). Never the text, the prompt, the reply, the suggestion, an id, the nickname or the token; a capture test proves it.
- **(1.7) Dependency:** `@aws-sdk/client-sqs` `^3.1175.0` (same range as the other SDK clients) to send to the queue from the conversation function and the flags command; `@aws-sdk/client-bedrock-runtime` was already there (smoke). Fakes, not a mocking library, as in 1.4 (`platform/api/conversation/fakes.ts`).
- **(1.7) Notes for 1.8:** the page polls `GET /api/conversation/messages/{id}` every 2 seconds; a `flagged` status means "waiting for your facilitator" (it has no reply until a decision), and the 409 reasons `busy`, `waiting` and `no-nickname` tell the page what to show. - **Allow-list command layout (1.3):** `platform/src/allowlist/`: `logic.ts` (pure: arguments, CSV rules, path check, output text), `store.ts` (interface `upsert`/`listAll`, implemented on DynamoDB), `command.ts` (the whole flow with file reads, store and output passed in, tested against an in-memory store) and `main.ts` (wiring only). Root script `npm run -s allowlist -- import <file.csv> | list`, like smoke.
- **Allow-list dependency (1.3):** `@aws-sdk/client-dynamodb` `^3.1175.0` (same range as the other SDK clients); no `lib-dynamodb`, the two calls are short with plain attribute values.
- **Allow-list table name (1.3):** `TABLE_NAME = "ssd-workshop-data"` is a platform constant; a test imports `infra/lib/config.ts` and checks both are equal.
- **Allow-list upsert (1.3):** one `UpdateItem` per row on `allowListKey(email)` setting `type`, `email`, `group`, `role` and `createdAt = if_not_exists(createdAt, now)`, so a re-import changes group and role only and keeps `createdAt` and `participantId`; `ReturnValues: UPDATED_OLD` tells added (no old values) from updated. "Updated" counts every existing email, even when its group and role did not change.
- **Allow-list list (1.3):** a paginated `Scan` with filter `type = allow`, projecting only `group` and `role` (the addresses are never read); fine for tens of entries. Output is a table `Group / Role / Count`, groups alphabetical, roles in the order participant, facilitator, admin, then a `Total` line; group names go through the email masking in case an address ever lands in that column.
- **Allow-list CSV rules (1.3):** header `email,group,role` required as the first non-blank line (case and spaces ignored), UTF-8 BOM stripped, CRLF accepted, blank lines skipped, no quoted fields (a row without exactly 3 fields is rejected). Email: trimmed, lower-cased, ASCII only: local part `[a-z0-9._%+-]+`, domain labels `[a-z0-9-]+` separated by dots, alphabetic TLD of 2+ letters (no `_` in the domain; no accents or brackets anywhere); kept no wider than smoke's `redactEmails`, and a test checks every accepted form is fully masked by `redactError`. Role exactly `participant`, `facilitator` or `admin` after trim and lower-case. Group trimmed, non-empty, rejected when it holds an `@` (`group looks like an email address`), so an address pasted in the wrong column is never stored or printed; otherwise kept as written with no character restriction (the CSV format already excludes commas). A later line with an email seen earlier in the same file is rejected as `duplicate of line N`. A file without the header (or empty) imports nothing and exits 1.
- **Allow-list output (1.3):** `Added: N`, `Updated: N`, `Rejected: N`, then one `Line N: <reasons>` per rejected line (reasons `invalid email`, `empty group`, `unknown role`, `expected 3 fields, found N`, `duplicate of line N`, several joined with commas). Line numbers are 1-based file lines. No message ever holds an address; AWS errors are printed through smoke's `redactError` (addresses masked).
- **Allow-list exit codes (1.3):** 0 when the import ran, even with rejected rows (the valid rows are stored and every rejection is printed); 1 on a usage error, a refused or missing file, a file without the header, or an AWS error. If AWS fails halfway, the counts so far are printed before the error (re-running is safe: upserts are idempotent).
- **Allow-list file outside any repository (1.3):** the path must be absolute; a relative path is refused ("give an absolute path to the CSV file", exit 1), because through the root script `INIT_CWD` is the repository root wherever the command was typed, so `../people.csv` would silently read another file. The repository root is the nearest folder above `main.ts` whose `package.json` declares workspaces (`realpathSync.native`). The CSV is refused if it is inside that root as written (so a file that does not exist yet is refused too) or after `realpathSync.native` (symlinks), comparing paths case-insensitively (macOS ignores case and realpath does not fix it; a false refusal is harmless); if it has more than one hard link (`nlink > 1`, realpath cannot follow them); or if its real folder or any folder above it holds a `.git` entry (a folder in a clone, a plain file in a work tree or submodule; `existsSync` plus `lstatSync`, walking up to the filesystem root). No git subprocess: no git environment variable (`GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`), "dubious ownership" error or missing git can make the check pass a file that is in a repository. A path that is not a regular file is refused after the repository checks ("Refused: the CSV path is not a file."), before the hard-link check whose count means nothing for a directory. All checks run before the file is read and before any AWS client is created; a missing file is "CSV file not found."
- **CSV files ignored by git (1.3):** `*.csv` is in `.gitignore` as a second barrier (no tracked `.csv` exists).
